# CLAUDE.md - flowfile_core

Central FastAPI backend and DAG execution engine for Flowfile: manages flows as DAGs, runs node compute on Polars, hosts auth/catalog/secrets/AI/kernel subsystems, and offloads heavy work to `flowfile_worker`. Package-specific notes only; see the root `/CLAUDE.md` for monorepo-wide setup, build, lint, ports, and cross-package contracts.

## Role
- The hub of the system. The frontend (Tauri/web) and `flowfile`/`flowfile_frame` clients hit its REST API on **port 63578**; it calls `flowfile_worker` (63579) for compute, the kernel containers (Docker SDK) for sandboxed user code, and `flowfile_scheduler` for cron runs.
- App is `flowfile_core/main.py:app`; entry `flowfile_core.main:run` (poetry script `flowfile_core`). Also runs a saved flow in-process via `python -m flowfile_core.main --run-flow <path> --run-id <id> [--backend <id>]` (PyInstaller / CLI path; the run's backend is `--backend`, else a backend id saved as the flow's `execution_location`, else core's own (`local`) whatever a saved `local`, `remote` or `auto` says; it becomes the process's default through `registry.set_default_override` and the flow runs `"remote"` on it, or `"local"` on `local`; drops UI-only `explore_data` nodes). `--run-id` is required.
- **Core compute contract:** core never materialises full LazyFrames for dataset memory. A flow's `execution_location` is `"auto"` or a backend id (`local`, `worker`, `worker:<name>`, an entry point's), `"remote"` the legacy alias of `"auto"` (a plain string in `schemas.py`; an id is not checked against the registry); with `FLOWFILE_COMPUTE_PROTOCOL` on a new flow's is `"auto"` and a file saved `local` or `remote` opens as `"auto"` (`schemas.loaded_execution_location`, applied to every format by `io_flowfile._load_flow_storage`), with it off a new or `"auto"` location validates to `"local"` or `"remote"` and a file opens as saved. Each node's settings carry an `execution_location` too (`NodeBase`: `"auto"` by default, or a backend id), saved with the node (by `model_dump`, and by hand in the select, join, cross join, fuzzy match and output `to_yaml_dict`s) and among the AI planner's `_PLANNER_INJECTED_SETTINGS_FIELDS`; a run reads it only with an exchange store configured (`FLOWFILE_EXCHANGE_URI`, the mixed policy under Execution package), and otherwise every node of a run goes to the run context's backend but, with the protocol on, the Google Analytics reader, which its builder pins to the worker and which then runs, and submits its plan, under a context on the worker whatever the run's backend. A node's plan goes to the backend of the run's execution context (`ExecutionContext.for_flow`): `LocalBackend`, which holds it lazily in core, for a `"local"` flow; the registry's default backend for an `"auto"` or `"remote"` one, the worker unless `FLOWFILE_COMPUTE_BACKEND` (or, unset, `FLOWFILE_OFFLOAD_TO_WORKER=0`) says `local`, and the worker owns dataset memory in spawned subprocesses; the backend of that id for any other location; core ships plans and JSON. The bounded reads the engine makes of a plan (a count, a first row, an aggregate row, a pivot's distinct values) go through the current execution context's backend (`flow_data_engine/bounded.py`, see Key patterns) — don't add collects in core outside `LocalBackend`.

Its `--run-flow` verb is checked at the top of the file, **before** the router imports and the import-time `storage.cleanup_directories()` sweep, so a run child never deletes cache/temp entries the live core still references; the run verb lives in `flowfile_core/run_flow_cli.py` (`tests/test_run_flow_cli.py` pins that the sweep is skipped).

- `flowfile_core/flowfile/flow_graph/` — DAG execution engine package. `graph.py` is `FlowGraph` (construction, settings, node lifecycle), composed from mixins over the type-only `_base.py`: `history.py`, `canvas.py`, `builders/*.py` (one per node family; every `add_<type>` stays a method for `getattr` dispatch), `execution.py`, `persistence.py`; plain helpers beside them: `connections.py`, `catalog_resolution.py`, `catalog_write.py`, `cloud.py`, `freshness.py`. `__init__.py` is the facade and the **bind surface**: the collaborators listed at the end of its `__all__` are read through `_root.root()` at call time (see Gotchas; `get_db_context`/`CatalogService` only by `_resolve_virtual_table`, the rest of the package imports them directly). `flowfile/handler.py` — `FlowfileHandler` in-memory flow registry.
- `flowfile_core/change_feed.py` — the per-flow change feed behind `GET /editor/events` (`routes/routes.py`, next to `/editor/history_status/`): subscribes once to the bus events `flow_revision` (every `FlowGraph._bump_revision`: `graph` at the outermost `transaction` exit — stamped last, after `get_history_state`, and only when the persisted hash moved, so neither a failed nor a no-op request moves it — and for direct writes outside a transaction, successful undo/redo/`revert_if_top`; `run_started`/`run_ended` from `try_claim_run`/`release_run`; `saved` from `mark_as_saved`), `flow_closed` (`FlowfileHandler.delete_flow` and `evict_flow_by_path`) and `flow_rekeyed` (`rekey_flow`, a Save As: the old id's subscribers get `rekeyed` with `new_flow_id` and their stream ends), and hands them to per-flow asyncio queues with `call_soon_threadsafe` only, never blocking the mutating thread. `ClientOriginMiddleware` (pure ASGI, in `main.py`) reads `X-Flowfile-Client` into the `CLIENT_ORIGIN` ContextVar, which the threadpool route and the run's background task inherit, so every event names its origin. `subscribe(flow_id)` registers the queue and `_Subscriber.events(keepalive=)` yields `None` on an idle tick and ends on `closed`, `rekeyed` or `close_all()` (`stream()` composes the two); the route subscribes **before** it reads `flow.revision` for `hello`, so no change falls between. `close_all()` is called from `main._stop_server` (the `/shutdown` route, the parent-death watcher), from `main._Server.handle_exit` (uvicorn's `capture_signals` replaces the SIGINT/SIGTERM handlers while it serves, so `main.signal_handler` never sees them then) and the lifespan, because uvicorn waits for open connections before the lifespan shutdown. The route is `async def`, reads `flow.revision` and `is_running` without the edit lock, and streams through `ai/streaming.py`'s `SSEEvent`/`make_streaming_response` (imported in the function, like every `ai` import outside the package). Tests: `tests/test_change_feed.py` (asyncio unit), `tests/routes/test_events_route.py` (a real uvicorn on a loopback socket — the TestClient buffers whole bodies, so it cannot read an open stream), `tests/flowfile/test_flow_revision.py` and the `TestRevision` class in `tests/test_history_routes.py`.
- `flowfile_core/flowfile/settings_validation.py` — conservative static check that node settings only reference existing input columns (per-node-type extractor registry + `validate_flow_settings`); served by `GET /flow/settings_validation`, gated per flow by `FlowSettings.validate_settings`. Flowfile formulas (formula node, advanced filter) are covered by walking polars_expr_transformer's parse tree for `pl.col` references. A second phase (`@_expression_probe` registry) asks whether the expression can run at all via `_extensions/real_time_interface.check_expression` — the runtime parser (`simple_function_to_expr`) applied to an **empty LazyFrame** built from the predicted schema (`filter()` for the advanced filter, mirroring `do_filter`, which is what enforces Boolean-ness), so a type error like `[n] + "a"` surfaces on the canvas without touching data; `${param}` refs are resolved first and skipped when undefined. **The registry's entry criterion is "columns whose absence makes the node *fail*", not "columns the node references"** — `select`, `dynamic_rename`, `multi_field_formula`, and the join-family select lists skip missing columns and keep running, so they deliberately have no extractor (`multi_field_formula` gets no expression probe either — its `[_Current*_]` placeholders are not real columns, so the probe would fail on flows that run; `run_flow` too: its parameter columns arrive on keyed handle `input-0`, which `main_inputs` cannot address). `tests/flowfile/test_settings_validation.py::test_warning_matches_runtime_behaviour` pins this by running each node type with a renamed-away column and asserting warn ⇔ failure, with a control run proving attribution — add a case there before adding an extractor. Warns only when the input schema is confidently known: no extractor (custom nodes, raw polars/SQL/python code), blocked or failed prediction, and empty schemas all stay silent — never add an extractor or probe that can false-positive.

The browser *executes* advanced filters correctly now — same `simple_function_to_expr` core uses — but the expression string still cannot travel, because that parser executes Python for a crafted formula; a basic filter carries a column, an operator and a value, none of which is evaluated. Deliberately narrow because WASM converts a basic value by the column's dtype while core lits it as written (temporal columns excepted: a basic filter on a Date/Datetime column wraps the value in `to_date`/`to_datetime` in core and `fromisoformat` in the browser, so an ISO literal runs on both sides) — only whole numbers and text literals are provably the same expression on both sides, and a fractional bound, a boolean/null literal, or anything with a function call, a second condition or a column on the right stays a placeholder), `transform.py` (live `FlowGraph` → `{v:1, flow}` envelope; explicit `connections` always; placeholders = sentinel `<type>__unsupported` + stripped stub carrying only the user-typed description), `encoder.py` (deflate-raw+base64url, `decode_share_hash` inverse; target URL constant). - `flowfile_core/flowfile/converters/alteryx/` — Alteryx `.yxmd` importer: `yxmd_parser.py` (XML → tools/connections), `mappers.py` (per-tool node emitters), `expression.py`, `convert.py` (layout, wiring, validated `FlowfileData`), `report.py` (`ConversionReport`/`ToolReportRow`, statuses `converted|partial|commented|placeholder|out_of_scope|no_op|skipped`; every row also carries a required `reason` — why it has that status, from a closed vocabulary, so the numbers group without parsing English — and a `census_name`, the tool's identity for scope and grouping, which for a macro is its bare filename). **Formula translation is fail-closed** — an Alteryx expression is emitted only when it tokenizes, resolves every function through `FUNCTION_MAP` *and* round-trips the real Flowfile parser, otherwise the original text is preserved as a `//` comment above a safe stub (and an unsupported tool becomes a `polars_code` passthrough placeholder), never a best guess. **Every placeholder embeds the tool's original `<Configuration>` XML plus its Alteryx annotation as `#` comments**, so a node can be rebuilt without the source `.yxmd` (comments are stripped by `polars_code_parser` before execution, so they cost nothing at run time). Alteryx `NOT`/`!` translate to `not(...)`, but `IN` never does — Flowfile's `in` is substring containment, not set membership. Of Alteryx's three MD5 functions only **`MD5_UTF8` maps** (onto polars-expr-transformer's `md5()`, which hashes UTF-8 bytes); `MD5_ASCII` (narrow/Latin-1 bytes) and `MD5_UNICODE` (UTF-16LE) hash *different bytes* and stay rejected with a reason pointing at `MD5_UTF8` — Alteryx's own worked example `Md5_Ascii('Lá')`/`Md5_Unicode('Lá')`/`Md5_Utf8('Lá')` gives three different digests, pinned in `test_expression_translator.py`. `Base64Encode`/`Base64Decode` map onto `base64_encode()`/`base64_decode()` over the UTF-8 bytes of the text, without a caveat (identical for ASCII under any encoding). There is deliberately **no hex mapping**: Alteryx's `IntToHex`/`HexToNumber` are integer radix conversions, not the byte-level encodings `hex_encode()`/`hex_decode()` provide. Beyond the obvious 1:1 tools, `DynamicRename` maps onto the native `dynamic_rename` node (formula / first_row / prefix+suffix) or, for the right-input modes, is resolved at import time into a plain `select` when the name source is a readable Text Input; `MultiFieldFormula` maps onto the native `multi_field_formula` node, with the `[_CurrentField_]` / `[_CurrentFieldName_]` / `[_CurrentFieldType_]` placeholders preserved verbatim (they are the only `[_X_]` specials the translator accepts, via `try_translate(..., allowed_specials=...)`) and Alteryx's `FixedDecimal(size, scale)` output type stored as `Float64` with size and scale dropped. A **declared string output type is deliberately ignored** (the tool echoes the selection's own type into `OutputFieldType`, so a text-mode tool says `V_String` without meaning "stringify"): casting to text is a no-op when the expression already returns text and irreversible otherwise — Polars cannot cast text back to Boolean, so `price_paid.yxmd`'s `[_CurrentField_]='Y'` into a downstream Select retyping the column to `Bool` would break — and keeping the produced type is always recoverable. `RegEx` parse/match/replace becomes generated Polars code (rejected fail-closed when the pattern uses lookaround or backreferences, which Polars' regex engine lacks); and simple-mode `Filter` triples are rebuilt into an Alteryx expression and run back through the same translator. A headerless `Input Data` tool also emits a `select` renaming Polars' `column_1..N` to Alteryx's cached `Field_1..N`, without which every downstream reference to an Alteryx column name silently misses. `RecordID`, `CrossTab` (pivot; always `partial` because Alteryx underscores the new column names and Flowfile keeps raw values), `AppendFields` (cross_join), `RunningTotal` (window_functions `cum_sum`, `RunTot_<field>` names) and `Transpose` (unpivot chained into a `variable/value` → `Name/Value` rename select) also map onto native nodes; `Switch`, `ReplaceChar` (nested literal `replace()`s) and `DateTimeFirstOfMonth`/`LastOfMonth` translate in the formula dialect, and the emitter parenthesizes compound `=` operands because polars_expr_transformer gives `=` maximum binding power. Macro tools carry no plugin name (`tool_name` is empty), so `get_mapper` dispatches them through `MACRO_MAPPERS`, keyed on the `EngineSettings Macro` filename basename; the Data Cleansing macro (`Cleanse.yxmc`) maps onto the native `data_cleansing` node — its config is the macro's flat question-value list (`<Value name="Check Box (N)">`), whose widget ids are matched by name and fail closed on any missing or unrecognized entry rather than guessing by position — and the Count Records macro (`CountRecords.yxmc`) onto `record_count` chained into a select that renames `number_of_records` to Alteryx's `Count` (Int64). ## Key patterns & conventions
- **Router wiring is centralized:** add endpoints by including the router in `main.py` (order/prefixes there are load-bearing — e.g. `ai_admin_router` mounts on `/system`, not `/ai`, so admins can flip the gate). Most editor routes carry `Depends(get_current_active_user)`; `public_router` and `flow_api.data_router` are API-key-authenticated (`verify_api_key`) instead.
- **In-memory flows are per-session; resolve them for the caller.** A flow id is not a secret (the flow's file stores it and `import_flow` reuses it), so every logged-in route that names an open flow resolves it with `routes.get_flow_or_404(flow_id, current_user)` (AI/ML/log routes call `flow_file_handler.get_flow(flow_id, current_user.id)` and keep their own status codes); another user's flow answers exactly like a missing one. `get_flow(flow_id)` without a user is unscoped — internal callers and lookups after a scoped check only. `import_flow` gives the flow a fresh id (and a fresh per-id `FlowLogger`, which the `flow_id` setter does not rebind) when its stored id is open in another user's session, and `register_flow` refuses a taken id without evicting the holder. `tests/sharing/test_flow_session_isolation.py` builds its route list from the live app and fails on any unscoped lookup of another user's flow; exempt a route there, with a reason, only when its `flow_id` does not name an in-memory flow (catalog registration ids, kernel namespace keys, the token-signed `/raw_logs` sink).
- **AI gate:** the whole `/ai/*` router is gated by `FEATURE_FLAG_AI` (live-mutable `MutableBool` in `settings.py`; `ai/feature_flag.py` `is_ai_enabled`/`require_ai_enabled`, returns 503 when off). The `/system` admin route flips it without restart.
- **Keep the `ai` package litellm-import-free at module level.** Every `import litellm` is lazy (inside functions): `ai/providers/_litellm_base.py` and `ai/scheduler.py` (`from litellm import exceptions`). `ai/__init__.py` `setdefault`s `LITELLM_LOCAL_MODEL_COST_MAP=True` before any lazy import. Re-adding an eager litellm import breaks `test_classification`/`test_dry_run` lazy-contract tests. BYOK key wiring lives in `ai/byok.py` (reads `ai/credentials.py`, sets provider env vars litellm picks up); providers registered in `ai/providers/registry.py`.
- **Secrets format:** `encrypt_secret(secret_value, user_id)` → `$ffsec$1$<user_id>$<fernet_token>`; key is `HKDF-SHA256(master_key, info="user-<id>")`. The embedded user_id lets the worker decrypt without user context; legacy raw-Fernet tokens still decrypt via the `user_id` param.
- **API-key hashing is deliberate SHA-256** (`auth/api_key.py:hash_api_key`) — 256-bit random tokens, not passwords; don't "upgrade" to a KDF (the CodeQL weak-hash alert here is a known false positive). Passwords use bcrypt (`settings.PWD_CONTEXT`).
- **Kernels:** `kernel/manager.py` allocates host ports from **19000–19999** (`_BASE_PORT=19000`, `_PORT_RANGE=1000`) per container; image flavours (`ImageFlavour.BASE/ML/LITE/NOTEBOOK/CUSTOM`) resolve their package inventory from `kernel/kernel_image_manifest.json`, generated from `kernel_runtime/{pyproject.toml,poetry.lock,Dockerfile}` by `tools/generate_kernel_manifest.py` and read package-relative in `kernel/flavours.py`. Image *tags* live in `kernel/images.py` (docker-free, so `matching.py` can read them without pulling in the docker SDK); `manager.py` re-exports them. **Creating a kernel pulls a missing image itself**: `create_kernel` runs `_ensure_image(base_image)` in `POST /kernels/`, and `_build_derived_image` calls it too, so a package edit pulls as well. It is an inline `_do_pull` (refs split by `docker.utils.parse_repository_tag`, so registry ports and `@sha256` digests survive) that waits on a `start_image_pull` already in flight and records the same `pulling`/`error:<msg>` pull state, so `docker-status` reports it like a background pull; a failed pull is the route's 409 `Failed to prepare kernel image: …` and the kernel is never registered. Starting a kernel pulls a missing base image the same way (the pin moves with an app release for the notebook flavour), and a derived image is reused only while its `flowfile_base_image` label names today's base — otherwise it is rebuilt on the new one. **How a kernel reaches core is `kernel/urls.py::core_base_url` and nowhere else** — both `_build_kernel_env`'s `FLOWFILE_CORE_URL` and `execution.py`'s `/raw_logs` callback go through it, keyed on `_docker_network` (the kernel resolves core by service name only when it was joined to core's network) and using `settings.SERVER_PORT`, never a literal. Two independent constructions with a hardcoded `63578` in one of them is how the desktop app, which port-scans for a free pair, ended up sending a kernel's API callbacks to a different process than its log callbacks. **Startup GC is fail-closed and ownership-scoped.** `_restore_kernels_from_db` returns whether the registry is authoritative; when it isn't, `__init__` skips the orphan-container reap and the derived-image GC entirely (adoption still runs — it only adds knowledge). One swallowed DB error used to leave `_kernels` empty and the GC passes read that as "nothing should exist", destroying every container and image. Containers now carry ownership labels: `flowfile_core_instance` (which install, stable) and `flowfile_core_runtime` (which *process*, per-boot). Reaping needs the install label plus a 10-minute age grace; `shutdown_all` stops only kernels in `_started_here` — the DB-shared registry also lists kernels another core started, and tearing those down is how quitting the desktop app killed a dev core's kernels. `FLOWFILE_KERNEL_GC=0` disables reclamation outright. Shutdown duty transfers on adoption when the owning pid is gone (`_claims_ownership`, reusing `shared/run_completion._pid_is_alive` — `os.kill(pid, 0)` kills on Windows, so never probe by hand), so a hard-killed core doesn't leak its containers forever while a *live* owner keeps its own. Pre-label containers and pids recycled across a reboot leak instead; that direction only leaks, never kills another core's kernel (`make clean_kernels` is the manual sweep). The `get_kernel_manager` singleton is lock-guarded and warmed by a best-effort daemon thread at startup (`FLOWFILE_KERNEL_WARMUP`, default on; forced off in `tests/conftest.py` so TestClient lifespans never touch Docker). `KernelManager` construction first probes the daemon with a short-timeout client (`_DOCKER_PROBE_TIMEOUT_SECONDS`) and the kernel routes fetch the manager via `asyncio.to_thread` — never call `get_kernel_manager()` or `docker.from_env()` directly from an async handler, because a hung daemon then freezes every request in core (`docker.from_env()` negotiates the API version under the SDK's 60 s read timeout, on the event loop). Starts are **single-flighted** per kernel (`_start_flights`) and container creation converges on name conflicts via a bounded create-or-adopt loop (`_create_or_adopt_container`: adopt the holder if it runs the desired image ID, else replace it). Execution is **serialised per kernel** (`_exec_locks`, one cell at a time) because the runtime execs cells into a shared namespace in one interpreter — concurrent cells race imports; `/interrupt` deliberately takes no locks so a running cell can always be cancelled. **Cancellation is addressed to an execution, never to a kernel**: every `ExecuteRequest` carries a server-minted `exec_token` (`build_execute_request` for flow runs, `execute_sync` for everything else; the `/execute[_cell]` routes blank any client-supplied value), `_active_execs[kernel_id]` records which token holds the exec lock, and `interrupt_execution_sync(kernel_id, exec_token)` refuses to fire unless that token is the one running. Without this a flow queued behind another flow on a shared kernel cancels the *other* flow's cell — `FlowNode.cancel` must always pass its own token, and the kernel's `/interrupt` binds the token to that cell's generation (a token whose cell already finished interrupts nothing rather than falling back to the newest cell). **Dependency matching** (`kernel/matching.py`, `packaging`-based, pure): `POST /kernels/match` (and the digest form `POST /kernels/match/batch` powering list-view readiness badges) ranks the caller's kernels against a custom node's pip specs (version-aware; a kernel "provides" = manifest packages for its flavour ∪ requested `packages` names ∪ `resolved_packages`) and returns a create-from-spec `KernelConfig` seed (ML flavour inferred from dep names, slugified collision-free id); it **degrades to DB-persisted kernels when Docker is down** — no 503. At run time `flow_graph/builders/custom_nodes.py::_execute_on_kernel` pre-checks a kernel-env custom node's deps (`verify_kernel_for_node` → typed `KernelDependencyError`); only *provable* mismatches block — unverified versions, unknowable images, and invalid specs never do.
  **A kernel whose contents can't be enumerated is `level="unknown"`, never `"full"`.** That covers a custom image, a flavour repointed by `FLOWFILE_KERNEL_IMAGE_*` to a different release than the manifest describes, and a missing manifest. Collapsing that into `full` is what made every packaged install report "✓ has all packages" for kernels that had none, so keep `unknown` distinct from `unverified` (which means the image *was* enumerated and the name was found, but the version or extras aren't provable). `tests/test_kernel_packaging_gate.py` keeps the missing-manifest case unreachable in shipped artifacts; `tests/test_kernel_dependency_gate.py` (`-m kernel`) checks the manifest against a real `pip list` inside the image.
- **Kernel code-intelligence bridge:** `kernel/routes.py::_lsp_forward` takes any pydantic `BaseModel` (it only `model_dump()`s) and every not-ready condition degrades to an empty 200. `POST /{kernel_id}/lsp/dataframe_schemas` is the column-completion route: it returns `DataframeSchemasResponse`, whose `state` defaults to `"unavailable"`, so a `{}` from the bridge (flag off, no Docker, kernel missing/not-owned, a pre-0.6.0 image 404) is already the right shape. `manager._lsp_unsupported_warned` is keyed `(kernel_id, op)` with op-aware text — an image that serves `complete` but 404s a newer op must not log "has no code-intelligence endpoint" and then suppress the warning for the ops it genuinely lacks. The mirrored `DataframeSchemasRequest` carries an opt-in `resolve_lazy_frames` (default off), forwarded verbatim like every other field: with it set the kernel resolves each `LazyFrame`'s schema — planner-only, but a scan can still do I/O — instead of reporting it `unresolved`. The frontend does not send it yet. `ExecuteResult.namespace_generation`/`revision` are optional passthroughs of the kernel's namespace identity (absent from an older runtime ⇒ defaults), which is how the editor rejects schema metadata minted by a different namespace instance.

- **Settings are `MutableBool`** so they toggle live: `SINGLE_FILE_MODE`, `OFFLOAD_TO_WORKER`, `FEATURE_FLAG_AI`, `FLOWFILE_AI_LOG_PROMPTS[_SCRUB]`, `FLOWFILE_COMPUTE_PROTOCOL`.
- **Conditional execution is a local trigger rule, never a closure.** `flowfile/util/skip_rules.py` classifies every node from its *immediate* inputs in topological order (`classify_graph` for the plan, `classify_from_inputs` per stage in `_execute_stages`); `node_skipper` and `get_all_dependent_nodes()` are thin wrappers over it. **ALL** is the rule for every node (an error-ish input ⇒ `SKIPPED_ERROR`, else a deliberately-skipped input ⇒ `SKIPPED_DELIBERATE`); **ANY** is `union` **only** (`ANY_INPUT_NODE_TYPES`) — the other multi-input types address inputs positionally (`input_df_1..N`), so eliding one would silently renumber the rest. Failure never inherits ANY: a failed branch must not become "half the data written successfully". The two skip *causes* must stay distinct — error-ish (misconfiguration, failure, cancellation) blocks everything downstream as before, while **deliberate** skips originate only from gates routing a side dead and are a *successful* outcome: `NodeResult(success=True, skipped=True)` rows (`_record_deliberate_skips`) so the run stays green and `nodes_completed` still reaches `number_of_nodes`, and `_run_post_execution_callbacks` treats them as complete so a Kafka source upstream of a closed gate still commits its offsets (it only logs a warning when a gated-off *output* node is involved). Gate timing is split: **parameter**-mode conditions resolve before the run (`_evaluate_gate_conditions` → `closed_gate_handles` → `compute_execution_plan`; an unevaluatable condition is left *open* so it fails visibly at the node instead of silently picking a branch), **formula** conditions (a flowfile-formula row predicate; open iff ≥1 row matches, checked against the control input when connected else the gate's own data input, `${param}` refs resolved with the run's params) are decided in the stage loop after the gate executes (a bounded `filter().head(1)` in `_gate_formula_matches`, collected in core, or with `FLOWFILE_COMPUTE_PROTOCOL` on read through `bounded.head_rows` on the run's backend, or outside a run (`ff.Gate.is_open`) on the gate's graph's; folded into `closed_gate_handles`) — which is why `executor.py` gives formula gates an unconditional **always-run** decision alongside output/`run_flow` nodes: the checked data can change without any hash changing. Legacy `control_input`/`invert` gate settings migrate on load (`GateInput._migrate_legacy_shape`: source → formula; inverted parameter operators flip to their complement). Gate closure is **per output handle**: an opt-in `NodeGate.else_output` gives the gate a second exit (then=output-0 / else=output-1; `output_names` property, filter-split pattern — no NamedOutputs, both handles serve the passthrough via `get_output`'s fallback), and `closed_gate_handles: dict[gate_id, frozenset[dead handles]]` (`dead_gate_handles()` in skip_rules: open+else→{output-1}, closed+else→{output-0}, closed+no-else→BOTH so a stale else edge left by toggling the option off never leaks); `effective_input_status` takes the edge's source handle (from `_slot_input_pairs`/`_input_output_handles`), a FAILED gate still kills every handle, and the union's `_skipped_input_ids_this_run` is (source id, handle)-keyed. Known limitation: `_input_output_handles` keys one handle per source, so both exits of one gate cannot wire into the SAME consumer (pre-existing filter-split limitation). A routed gate is itself `RUN`; only its dead-handle consumers read it as skipped. Two cache invariants make gate flips safe: (1) **a node that did not execute this run has not run** — every skipped node's `has_run_with_current_setup` / `has_completed_last_run` are cleared on both `node_stats` and `_execution_state`, or dev-mode serves the previous run's frame; (2) an ANY-rule node's **surviving-input signature** is tracked in `FlowGraph._any_input_liveness` and a change calls `invalidate_cache()`, because the node hash folds only settings + input hashes and would otherwise serve the previous run's partial concat (also from the worker's `cache_results` lookup). A gated-off union input is **dropped** — the union outputs only the surviving branches, so a dead branch's unique columns are simply absent from the output (edit-time schema prediction stays gate-blind and still shows the union of all branches). Gate-blind callers (code export, single-node fetch validation) omit `closed_gate_handles` and deliberately plan as if every gate were fully open. Only the Polars export emits gates as real if-blocks from the shared base machinery (condition atoms are signed `(gate_id, needs_open)` pairs — else-side consumers render `if not (...)`, except that adjacent blocks whose conditions are one gate's exactly-complementary singleton pair fuse into a real `if`/`else` via `_conds_are_complementary`; shared prefixes, different gates, and multi-atom sets never fuse because the else of `if P and g` is not `P and not g`) — never as `df.gate(...)` calls, which would be silently ignored by the rebuilt graph's pull-based execution; unions render as guarded list-appends — each branch appends its frame to a list under its `if` guard and the union concatenates the list, so a gated-off branch simply isn't in it — except a two-input union whose guards are exactly that complementary pair, which collapses to an `if`/`else` assignment, and the all-guarded empty-frame fallback (`if not <list>:`) is emitted only when no complementary pair proves the list non-empty (independent gates); pre-initialized empty stand-ins survive only for gated return values (`_empty_frame_schema_expr`); the formula row-probe helper gets its frame via `_gate_probe_expr`, with the `pl` import registered eagerly in `_compute_gate_conditions` because imports serialize before the gated body renders. The FlowFrame and project exports (the `ff` dialect) skip that machinery (`_compute_gate_conditions` is a no-op there) and place `ff.Gate(...)`, consumers reading `.then`/`.otherwise` — the same statements the canvas notebook shows as fused cells.
- **Catalog data freshness is version-addressed, never TTL'd.** Three coordinated mechanisms keep every surface current when a Delta table changes (including out-of-band writes): (1) `FlowGraph._refresh_catalog_reader_freshness` runs at every `run_graph` start — it probes live Delta versions (`catalog/delta_utils.py::get_live_delta_version`, cloud-aware) against the fingerprint stored in `NodeExecutionState.source_version_info` and calls `FlowNode.invalidate_cache()` on drift, which bumps `_cache_epoch` → rotates the node hash → defeats both the Development-mode skip and the explicit `cache_results` worker lookup, cascading downstream (pinned `delta_version` readers are never probed — deliberate time travel; readers over non-optimized virtuals invalidate every run, like `run_flow`). (2) Viz session keys (`catalog/services/visualizations.py`) fold live versions in: `tbl:{id}:v{version}`, SQL digests include referenced-table versions, fvt keys embed the snapshot filename+mtime — a write rotates the key and the stale worker child idles out (no push-evict; the endpoint exists for ops only). (3) Virtual-table resolution: `check_source_versions_current(None)` is **fail-closed** (no fingerprint ⇒ stale ⇒ re-run the producer); `_collect_source_table_versions` is **complete-or-nothing** (any unfingerprintable source ⇒ `None`; a flow with zero catalog sources stamps `"[]"` — provably complete, keeps plan replay); callers key the worker IPC cache via `fresh_versions_hash()` **after** resolution (identity-map-bypassing `get_table_fresh`), and the worker names that cache by `(table_id, plan_bytes, versions_hash)` with `NO_VERSIONS_HASH` always rebuilding. The sink writes `<result_id>.arrow.part` beside it, moved into place only once the sink returns, so a sink that fails leaves no file at the result path and nothing held; what Polars writes to the partial file after the error goes with the id's next `release` or submit, or the startup sweep. Every other plan, and every plan with the flag off, is held as it is, and no sample comes inline either way (`sample` computes one when a preview is opened), so nothing in core computes or copies a deferred node's rows before something reads them and a deferred chain composes over one in-memory frame. A result crosses to another backend only through `export` and `import_uri`: `export(ref, uri, credential)` writes a held result to `uri` as parquet by a streaming `sink_parquet` of its plan, nothing collected, and returns `uri` (a failed sink's Polars error propagates and the target is left to the caller); `import_uri(uri, schema, row_count, credential)` holds a `scan_parquet` of `uri` deferred under a fresh id with the schema and row count the caller gives, reading nothing (`count` answers the given count, the file need not exist until rows are read), and its `release` leaves the file. With `FLOWFILE_COMPUTE_PROTOCOL` on, `run_graph` places the nodes its execution plan runs before any of them starts and before kernel artifacts are prepared: `execution/placement.py::place(flow, backends, policy, nodes=)` assigns each node a backend by its policy, `SingleBackendPolicy(backend_id)` without an exchange store, the run's backend for every node but `google_analytics_reader`, which its builder pins to the worker (`_PINNED_BACKENDS`), and `MixedPlacementPolicy(backend_id)` with one (`FLOWFILE_EXCHANGE_URI` set), the backend a node's own `execution_location` names, the run's for `"auto"`, a pinned type where its builder pins it; and refuses the node when that backend's `Capabilities` lack its operation among `operations`, a scheme among `read_schemes` or `write_schemes`, a plugin among the keys of `plugins`, or, for `needs_kernel`, `file` among `write_schemes` (the kernel shared volume is on core's host); connections are not compared. A Run Flow node is placed with the flow it runs: that flow is built for the call by `manage/ephemeral_graph.py::ephemeral_flow_graph`, and the nodes its run would run are placed on the node's backend by the same policy (`placement._child_run_nodes`: the child's parameters take the node's constant bindings, read with the parent's parameters in the node's settings as the run puts them there (`parameter_resolver.node_parameters_resolved`, so a constant `${name}` forwards the parent's value; a nested flow's are the ones the walk gave it, and a constant `${name}` of one that is bound from a column a level up counts as a column binding in turn, `_column_bound_parameters` on the child carrying them down), its parameter gates are decided on them and the execution plan leaves out what a closed gate or the classifier skips, as `run_graph` plans a run; a gate on a parameter the node binds from a column, or whose value refers to one, is decided by each run from its row, so nothing behind it is placed there and the child's own run places it; the nodes behind a formula gate are placed, as the run places them), its own Run Flow nodes in turn up to `subflow.MAX_SUBFLOW_DEPTH`, and each of them refused there refuses the Run Flow node, the reason `node <id> of the flow it runs ("<registration name>") cannot run on backend "<id>": <reason>`; any error while the flow is resolved, built or placed (a reference that does not resolve, a file that is not a flow, a builder that raises) claims nothing, with a warning on core's log naming the node and the flow, so the node fails when it runs. A catalog writer's namespace is the one its `namespace_full_name` names, else its `namespace_id` (neither: the default namespace's local directory), a reader's its `catalog_namespace_id` (a reader without one claims no storage), and one on local disk is refused as `namespace "<catalog.schema>" is on local disk; remote execution needs an object-storage namespace`; a namespace whose storage cannot be located claims none, so the node fails when it runs. `place` answers a `Placement(assignment, boundaries, refusals)`, `boundaries` the `(source id, target id)` pairs of an edge whose two nodes are assigned to different backends, once each, every `Refusal` `Refusal(node_id, backend_id, reason)` the unmet requirements in words joined by `; `. The run asks each backend it names for `capabilities()` once (`GET /v1/capabilities` on the worker); one that raises a `ComputeError` is left out of the map `place` is given, and a node whose backend is not in that map is neither assigned nor refused, so it meets the typed error when it runs (reaching a backend is the handshake's); an id the registry does not know refuses every node assigned to it with the registry's message. Any refusal ends the run before a node starts: one failed `NodeResult` per refused node on the run report, its error `cannot run on backend "<id>": <reason>`, and nothing prepared, executed, skipped or committed (`nodes_completed` 0, `success` false). The run report carries the placement's `boundaries` as `RunInformation.boundaries`, a refused run's included. With the flag off nothing is placed and `boundaries` is `[]`. `trigger_fetch_node` places the node it runs and the nodes it reads from by `_place_run`, under an `ExchangeRun` of its own held as `exchange_run` and removed when the fetch ends: a refusal is recorded as a run's is and nothing runs, and a placement that raises fails the node's row with the error (`compute_error` its class for a `ComputeError`), raised again, and runs nothing; otherwise the node runs under the run's context on the backend placement assigned it, the edges into it from inputs that ran with their current setup as its `_boundary_inputs`, an input that has not run composed into its plan, and the fetch's report lists the boundaries into the node. `execution/exchange.py` is the exchange store, the object-storage prefix results cross between backends through: `FLOWFILE_EXCHANGE_URI`, an `s3://` root, `FLOWFILE_EXCHANGE_CONNECTION`, the stored cloud connection that opens it, and `FLOWFILE_EXCHANGE_MAX_ROWS`, the most rows an input may cross with, read per call (`settings.get_exchange_uri`, `get_exchange_connection`, `get_exchange_max_rows`: unset or empty no limit, anything but a whole number a `ValueError` naming it). `exchange_store(user_id)` answers `None` without the URI, else an `ExchangeStore(uri, credential)` whose `CredentialRef` names the connection found for that user (own first, then the lowest-id group grant), which core and the worker both resolve; the URI without the connection, a scheme other than `s3` and a name the user has no connection under are each a `ValueError` naming it. `run_graph` holds an `ExchangeRun(flow_id, run_id)` as `FlowGraph.exchange_run` from before `flow_run_started` is published: `prefix(user_id)` answers `<uri>/<flow id>/<run id>/` and the store's reference (`None` without a store) and remembers the store, and when the run ends, however it ends, `collect()` deletes every object under the prefix of each store remembered (`remove_prefix`: a boto3 client over the connection as core resolves it, a page listed and deleted at a time; no store remembered, no call) and `exchange_run` is `None` again; a failure to remove is a warning on the flow log and never the run's outcome. Under the mixed policy each boundary crosses through that store: `_place_run` resolves it for the upstream node's user (`exchange_run.prefix(user_id)`; the store's `ValueError` refuses the importing node with its message) into one `flow_graph/execution.py::BoundaryEdge` per output of the upstream node the importing node reads, keyed `(source id, source handle)` as the node looks its slot up, and `_execute_single_node` runs each node under the run's context on its own backend with its edges set as `FlowNode._boundary_inputs`; the node reads that input through `BoundaryEdge.cross()`, whose first call exports the upstream output to `<prefix><from>-<handle>-<to>.parquet` (an output other than the default submitted deferred as `<hash>_<handle>_<to>` for the export and released after it) and imports it on the node's backend, the import named among the node's submit `inputs` and released once the node ran (a failed release a warning on the node log); a node the run skips exports nothing. `_place_run` also refuses the importing node of an edge whose output core knows before the run to hold more rows than `FLOWFILE_EXCHANGE_MAX_ROWS`, naming the rows, the columns and the limit (`BoundaryEdge.cost`: the `row_count` of the result the upstream holds on its backend under its current hash, else the known count of the engine core holds for that output, the last run's while the upstream has run with its current setup, or a manual input's own frame; nothing is counted, sampled or collected to price it), and of every crossing while the limit is not a whole number; an edge whose count is unknown crosses whatever its size. The importing node is submitted with `must_materialise` in every type, a sink included, and stores each of its other outputs beside that result under `<hash>_<handle>` (`FlowNode._store_other_outputs`, released with the result), its handles then reading those stored results, so no result refers to the prefix once the run removes it. `NodeResult.compute_error` names the kind of failure a row is, in both flag states: `"Refusal"` on a refused row, the class name of the `ComputeError` that failed the node (`ComputeUnavailable`, `VersionMismatch`, …; the class the executor records as `_last_exception_class`) on a failed row of `_execute_single_node` or `trigger_fetch_node`, `None` otherwise. With `FLOWFILE_COMPUTE_PROTOCOL` on, a node function does not resolve its input's plan either: `FlowDataEngine.polars_schema()` answers from the engine's cached schema; `do_filter`, `filter_split`, `change_column_types`, `do_select`, `join`, `do_group_by`, `apply_sql_formulas`, `get_record_count`, `make_unique`, `unpivot`, `do_window_functions`, `split`, `apply_multi_field_formula`, `solve_graph`, `explode_hierarchy`, `do_pivot` (and `apply_flowfile_formula`, which it calls for a pivot without index columns), `apply_dynamic_rename`, `apply_data_cleansing`, `do_cross_join`, `align_to_schema` (the Kafka, Google Analytics and REST API readers' alignment) and `execute_polars_code` (the Polars Code node, whose code runs a second time over the empty frames; code that collects its input still reads it), the union node's function (`flow_graph/builders/combine.py`), the Run Flow node's outputs (`flowfile/subflow.py`, over the schemas of the child's output engines; its data input reaches the child with the input engine's cached schema, its metadata columns are named from the child output engine's cached columns and its parameter rows are read through `bounded.head_rows` on the run's backend) and `apply_output_field_config` (`flow_node/output_field_config_applier.py`), build their output engine with the schema `_derived_schema` resolves over an empty frame of each input's cached schema (where a bounded read names the columns, the pivot values, the first row or the null profile, over the steps after that read); and `apply_formula_entries`, `explode_hierarchy_frame` and `utils.calculate_schema` take that cached schema in place of resolving the frame. The other node functions still resolve their output's schema from its plan, and with the flag off all of them do. A CSV read whose type inference fails is resubmitted at a higher `infer_schema_length` under `<hash>_infer<rows>`; a `TaskFailed` whose message names an exception class is re-raised as `RemoteExecutionError` with that class. `execute_node` takes no location: a caller outside `run_graph` enters `use_context(graph.execution_context)` (`trigger_fetch_node`, the virtual-table producer run). A node's held result lives in core, so a cache does not survive a core restart. A held result goes with what held it: `FlowGraph.delete_node` releases the node's, `FlowfileHandler.delete_flow`/`evict_flow_by_path` and an in-place `import_flow` call `close_flow` on the flow leaving the registry (every node's `remove_cache`), and after a `run_flow` child graph's run (`subflow.py`) and a virtual-table producer run only deferred results are released (`FlowNode.release_deferred_result`): a stored child result may be scanned by the parent's.
- **Typed compute errors.** `flowfile/execution/errors.py` is the typed error family for talking to compute (`ComputeError` and its subclasses). `subprocess_operations.results_exists` raises `ComputeUnavailable` (naming the worker URL) when the worker cannot be reached; `False` means only that the worker answered the result is not there. The cache check asks only about a stored (`"materialised"`) result the node holds under its current hash on the run's backend (`FlowNode.held_result`, then `exists`); a node holding none has no cache, and a held deferred plan is no cache, so a `cache_results` node in local mode with `FLOWFILE_COMPUTE_PROTOCOL` off, where `LocalBackend` holds every plan lazily, follows the ordinary rules (Development mode skips it after a successful run instead of rerunning it every run) and never asks the worker; with it on, the node's stored result in core's storage directory is its cache, as on the worker. `NodeExecutor.execute` records any `ComputeError` raised while deciding through the normal failure path (`_prepare_for_execution` + `_handle_error`): the node fails with the typed message, is never rerun in core and never read as a cache miss, and a cached node whose last run failed reruns past its cache, which clears the error and lets `FlowNode._do_execute` read the stored result back. Schema prediction (`FlowNode.get_predicted_resulting_data`) treats an unreachable worker as "needs run" with a warning, so it never fails on an outage. A worker that cannot run a task fails it typed through `errors.worker_failure`, using the worker's `error_kind`, which `BaseFetcher.error_kind` carries: a plan the worker cannot load fails the node with `PlanRejected` (so does the worker's time-limit kill, which it labels the same way), a killed child with `TaskFailed`, and nothing continues in core. The published data API answers 503 when the worker is unreachable and 500 for other compute errors, with generic detail on the public `/api/data/{slug}` route and the typed message on the owner's `/test` route. With `FLOWFILE_COMPUTE_PROTOCOL` on, a published run that fails raises the typed error of its first failed node, rebuilt from that node's run report row (`compute_error` and its text, `api_runner._first_compute_error`), so a worker unreachable when the run starts answers 503 like one gone before the final read; a failed row that names no compute error (the node's own failure, a placement refusal) answers 500, as every failed run does with the flag off.
- **Bounded reads.** `flow_data_engine/bounded.py` is how the engine reads a plan without holding it: `count_rows`, `head_rows` (an Arrow table), `single_row` (a dict of `pl.DataFrame.row` values; `ValueError` with the caller's message on an empty plan) and `unique_values` (the distinct values of a one-column plan, sorted, null first, at most `limit`, in the column's dtype; given the column's name, as `do_pivot` and `pre_calculate_pivot_schema` give it, it does not resolve the plan's schema) each submit the plan under a fresh `bounded_<hex>` id with `DEFERRED_HINTS` (no materialisation, no inline sample, so it stays deferred on both core backends), make one `count` or `sample` and release it in a `finally`, filed under flow and node `-1`. A backend failure propagates as its `ComputeError`; nothing falls back to computing in core. The engine sites read the current execution context's backend: `FlowDataEngine.get_number_of_records(backend=)` (the count `get_sample`'s evenly spaced sample needs; without a backend it still counts in process), `_peek_first_row_as_dict` (dynamic rename `first_row`), `_fetch_null_profile` (data cleansing `remove_null_columns`), `do_pivot` and `schema_callbacks.pre_calculate_pivot_schema` (the first 200 distinct pivot values, cast to text in core), and `_calculate_schema` → `utils.calculate_schema` (the schema with `describe`-style statistics as one aggregate row over the first million rows, built in core; the worker's `calculate_schema` task is no longer called). Column statistics (`column_stats.compute_column_stats(engine, column, backend)`) run on the backend `FlowNode.get_column_stats` is given, by default `current_context().backend`: outside a run that is the default backend, not the flow's, so with the worker configured a local node's stats aggregate on the worker (`/node/column_stats` passes none); a failed full query retries counts-only on the same backend, and a `ComputeError` there is `ColumnStatsUnavailable` (409). With `FLOWFILE_COMPUTE_PROTOCOL` on, the column's dtype comes from the engine's cached schema, never from resolving its plan, and two more readers of a node's result go through a backend: the formula editor's preview row (`extensions._first_preview_row`: the node's cached sample or `sample(ref, 1)` on the backend that holds its reference, a secondary output's row through `head_rows` on that backend) and `/node/data/export` (`head_rows` of the first `limit` rows on the flow's backend, its schema checks from the engine's cached schema, the CSV written in core by `LocalBackend`'s `file_write`), so none of them opens a backend's stored file in core. Outside a run a node's function runs in its graph's context: `add_node_step` gives the node `_execution_context_getter` (`current_context(graph)`), which `FlowNode` enters around its function in `get_resulting_data` and `_predicted_data_getter`, so a FlowFrame's build-time read of a local graph reads in core and a remote graph's on the default backend; a node a builder creates itself has no getter and its reads take the context they are called in. Tests: `tests/flowfile/execution/test_bounded.py`. `tests/flowfile/execution/conformance/` runs the protocol's guarantees over every backend in its `conftest.BACKENDS` (core's own process and the session worker): bounded rows, a backend refusing another backend's results, every table result carrying the schema of its rows, a blob held as a copy of its bytes, copied out to a `file://` URI and never planned over, sampled or counted (on the worker with the protocol flag on only), a result core requires materialised (by `LocalBackend` with the protocol flag on) and a wide one stored as the backend's policy says, a result exported to a URI and imported back as a deferred result of the same backend, with `export` refusing another backend's results, `run_op` refusing exactly the kinds `capabilities().operations` leaves out, and typed errors (out of reach, released, other versions).
- **Worker handshake.** The transport holds no worker URL: every function and fetcher in `subprocess_operations` (and `streaming.streaming_start`) takes `worker_url`, the worker's base URL, from its caller, `WorkerBackend` its own `url` and every other caller (the catalog services, the REST "Fetch sample" route, the published-flow runner, the custom-node dry run, the `/system/worker_pool` proxy, `FlowDataEngine`'s worker helpers, the startup print) `registry.worker_url()`; a `_worker_session` call names it and the route on it (`_worker_session.get("/status/x", worker_url=...)`). Every such request and every `/ws/submit` and `/v1/ws/submit` connect first calls `subprocess_operations/handshake.py::ensure_handshake(worker_url)` with that URL: the first worker contact in a core process, whichever URL it is for, fetches `GET /capabilities`, compares the seven `Capabilities` fields with `local_capabilities()` and runs one empty-frame plan per expression plugin; a difference is a `VersionMismatch` naming both sides, nothing is sent and nothing runs in core instead. `WorkerBackend.capabilities()` is the one worker read outside that gate (its own request, signed with the backend's token), so a caller can read a worker's versions and compare them with `capability_differences` itself, as the `/compute_backends/{id}/handshake` route does. A failed check, a `requests.ConnectionError` through the session or an `OSError` from the websocket connect re-arms it. So the first worker contact of any kind can raise `VersionMismatch` or `ComputeUnavailable` (neither is a `RequestException`), and every caller that degrades on `RequestException` handles `ComputeError` too: `clear_task_from_worker`/`cancel_task` log and return `False`, the fetcher poll loop fails the task, `trigger_apply_table_edits`/`trigger_add_key_column` and the virtual-table materialize raise `WorkerUnavailableError`, the catalog metadata/preview/history reads fall back as on a connection error, `/system/worker_pool` answers 503 `WORKER_UNAVAILABLE`, and the custom-node dry run answers an unreachable worker as a `load` error, at submit or while it follows its task through `WorkerBackend.status` (`ComputeUnavailable`), and lets any other `ComputeError` reach its route, which answers 500 with the message. The dry run's status, result, cancel and clear go through the worker backend (`status`, `task_result`, `cancel`) and `clear_task_from_worker`, the helper `release` uses, since no protocol call clears a task by id.
- **Reads that are not a node's result.** With `FLOWFILE_COMPUTE_PROTOCOL` on: the REST "Fetch sample" route runs `run_op(rest_api_read)` on the worker backend with the node's pagination capped at one page of `sample_size` records, samples that result and releases it; the published-flow runner reads a non-local run's response as `sample(ref, n)` on the api_response node's reference through the backend that holds it, `n` being `max_rows` clamped to 10 000, the worker's sample cap (an unset `max_rows` too), while a local run still collects in core; a virtual table's preview samples the reference its producer run holds (`VirtualTableService.held_virtual_flow_table`, which keeps it until the read is done) on that reference's backend and counts it for `total_rows`, and a table that resolves without a run (a query table, an optimized one whose sources are current) reads its plan through `head_rows` and `count_rows` on the current context's backend. None of them opens a file a backend stored, and the worker's virtual-table snapshot is read only with the flag off.

## Gotchas
- **A worker failure never continues in core.** A plan the worker cannot load, a killed or timed-out child, an unreachable worker or one on other versions ends the node with a typed `ComputeError` (`PlanRejected`, `TaskFailed`, `ComputeUnavailable`, `VersionMismatch`; `flowfile/execution/errors.py`), downstream nodes are skipped, and the published data API answers 503 or 500. Do not add a path that collects in core when the worker fails; in-core execution exists only on `LocalBackend`, the backend of a `"local"` flow or of a default set to `local`. An unreachable worker is never a cache miss: `results_exists` raises instead of answering `False`.
- **The first worker contact in a process is a handshake** (`flow_data_engine/subprocess_operations/handshake.py`): any call through the worker session or the WebSocket submit can raise `VersionMismatch` or `ComputeUnavailable`, neither of which is a `requests.RequestException`. A caller that degrades on connection errors must handle `ComputeError` too. No module but `configs/settings.py` and `flowfile/execution/registry.py` may read `WORKER_URL` or `OFFLOAD_TO_WORKER`, and the four execution directories must not gain an inline `execution_location` compare: `tests/flowfile/execution/test_inline_location_branches.py` asserts both counts are zero. Ask the registry (`default_backend_id`, `worker_url`, `child_env`) or the backend you hold, and read a run's parallelism from `current_context()`.
- **Never bind a patched collaborator in a `flow_graph` submodule.** Tests patch names like `get_kernel_manager` or `ExternalRestApiFetcher` on the package root, and several only assert a call did *not* happen, so a submodule importing its own copy passes while checking nothing. Read them as `root().<name>` and add new ones to the bind-surface block of `__all__`.
- `flowfile_core/__init__.py` runs `validate_setup()` then `init_db()` **on import** — importing the package has side effects (DB file creation, Alembic schema migration, default-user seeding).
- Don't route full-dataset compute around the execution context's backend (no collect in core outside `LocalBackend`), and don't add eager litellm imports anywhere under `ai/` — both break invariants enforced by tests.
- There is no package-level `pyproject.toml`; deps, scripts, ruff, and pytest config all live in the monorepo-root `pyproject.toml`. The local `.env` is read by `settings.py` via Starlette `Config`.
- Kernel / AI-local-model / Docker features need Docker available; absence surfaces as runtime errors, not import errors.
- **`FLOWFILE_SECURE_STORAGE_PATH` relocates the electron `SecureStorage` dir** (`jwt_secret` / `master_key` / `internal_token`). Set by `tests/conftest.py` and `flowfile_frame/tests/conftest.py` before any core import (`_storage = SecureStorage()` runs at `auth/secrets.py` import) so suites don't write into the developer's real `~/.config/flowfile`. **`flowfile_worker` honors the same var** (`flowfile_worker/secrets.py`) — it must, because core encrypts `$ffsec$` secrets with the master key in that dir and the worker re-derives it independently; a split store makes every worker-offloaded secret decrypt fail ("Task failed"). So a worker started by hand in another shell needs the var exported too, or core's suite (which reuses a running worker on an explicit `FLOWFILE_WORKER_PORT` or with `FLOWFILE_TEST_REUSE_WORKER=1`) will diverge from it. The electron `internal_token` is persisted there so CLI subprocess runs (manual + scheduled) present the same kernel→core token as the server.
- **The test session never silently reuses a worker on the default port.** With `FLOWFILE_WORKER_PORT` unset and something already answering on 63579 (a dev worker, or the desktop app's packaged sidecar), `tests/conftest.py::_claim_worker_port` moves the session to a free port at import and `managed_worker` starts a worker built from this checkout there (`poetry run flowfile_worker --port …`); the report header names the port. `FLOWFILE_TEST_REUSE_WORKER=1` opts back into reusing the running one. An explicit `FLOWFILE_WORKER_PORT` is used as given and a worker already listening there is reused, so a pinned port pointing at a stale worker still runs against it (`test_telemetry_events.py::TestWorkerOffloadedFailuresKeepTheirClass` then fails). The suite's worker still posts its logs to `CORE_PORT` (default 63578), so set a private `CORE_PORT` too when a live core is running.
- **The formula node holds an ordered LIST of entries.** `NodeFormula.functions` is authoritative; `function` is the legacy single-entry field. The after-validator fills `functions` from `function` and mirrors it back — the SAME object — only when there is exactly one entry, and the serializer drops the `function` key entirely for zero or 2+ entries so an older Flowfile fails visibly instead of silently running only entry 1. Entries are evaluated **sequentially** (`flow_data_engine/formula_entries.py::apply_formula_entries`, one `with_columns` + `collect_schema` per entry (resolved over an empty frame of the input's schema when the caller passes one, as `apply_sql_formulas` does with the protocol flag on); `FlowDataEngine.apply_sql_formulas` is the run-time wrapper and `formula_entry(position, FunctionInput)` the one place a declared type resolves to a cast target): entry N sees the base columns plus the outputs of entries 1..N-1, the deliberate opposite of `multi_field_formula`, which puts every expression in ONE `with_columns` so each reads the ORIGINAL values. Failures are attributed to a row by `FormulaEntryError(position, output_name, detail, kind)`. **One classifier words every failure**, on every surface: `build_expression` (parse) and `classify_polars_error` (missing_column / type) in `formula_entries.py` are what the run-time engine, the chain check *and* the preview's active-row evaluation (`extensions.py::evaluate_preview_entry`) all raise through, so the row strip and the preview banner can never disagree (pinned by `test_real_time_interface.py`'s parity cases); `classify_polars_error`'s optional `schema` argument is what lets a type error name the text column and the cast that fixes it — `text_dtype_hint`, shared with the single-expression `check_expression`. `parse_detail` curates the parser's non-`ExpressionSyntaxError` failures — an unclosed `[` is a bare `IndexError` ("string index out of range") from the tokenizer and becomes `column reference is not closed, add ]`; anything else non-parser becomes `expression could not be parsed` — raw `str(e)` of an internal exception never reaches the user. A `missing_column` close to an existing column (difflib, cutoff 0.6, judged against the schema the entry actually saw) carries a `ColumnSuggestion` and the hint is folded into `detail` itself (`column 'regiOn' not found, did you mean 'region'?`).
- **Edit-time formula checks walk the same chain.** `_extensions/real_time_interface.check_expression_chain(schema, [FunctionInput(...)])` resolves each entry by running `apply_formula_entries` itself against an empty LazyFrame (data-free) and translating `FormulaEntryError` into a positional `ExpressionIssue`, so the editor and the engine cannot drift and returns one positional issue slot + one accumulated schema per entry. Each step also **collects** that zero-row frame, because `collect_schema` alone accepts the `.dt`/`.str`/`.list` namespaces unexamined (`format_date` on a text column resolves clean and only fails on collect); that failure goes through the same `classify_polars_error`, so the extra depth costs no wording drift. **Cascade suppression is load-bearing**: a failing entry still contributes its declared output column (String under Auto), so one broken row does not light up every row below it. Blank expression ⇒ no issue and no column; blank output name ⇒ `config`; a duplicate output name warns (`duplicate`) on the later entry without blocking the run; an unclassifiable failure yields no issue at all. `settings_validation._formula_chain_issues` consumes it and drops `missing_column` issues (the column phase reports those, having subtracted earlier entries' outputs); it labels a single-entry node `Invalid formula:` and a multi-entry one `Formula N ("name"):`, matching `str(FormulaEntryError(...))` — both prefixes come from `formula_entries.entry_label`. `settings_validation.node_formula_chain_issue` is the chain counterpart of `node_expression_issue`: the first `type`/`parse` entry, which is what `add_formula` returns as `(False, message)` and what the executor's `_raise_on_invalid_expression` gate raises on, so a formula node fails at itself rather than at a downstream sink.
- **Two POST routes back the multi-formula drawer** (same router auth as `instant_result`, no trailing slash): `/custom_functions/formula_chain_check` returns `{available, base_columns, entries:[{issue, columns}]}` for the editor's *unsaved* entries (`available=false` when the input schema cannot be resolved — silence over guessing), and `/custom_functions/formula_chain_instant_result` evaluates entry `index` on the one preview row with the entries above it applied first. Logic lives in `flowfile/extensions.py`; the routes stay thin. A chain issue is `{message, kind, suggestion}` where `suggestion` is `{kind: "replace_column", from, to}` or null (`FormulaChainSuggestion`; `from` is a keyword, hence the `from_column` field + alias) — additive, so an older frontend ignores it.
- **Exported code must bind what the node had.** A Polars-code node runs in `PolarsCodeParser.safe_globals`, which provides `col`, `lit`, `cs`, `expr`, every dtype by bare name, `BytesIO`, `base64`, `datetime`, `time`, `decimal` and `zoneinfo` besides `pl`; the Polars export inlines the code, so `code_generator._sandbox_imports` adds the import for each of those names the code reads — the statements are **derived from the sandbox dict itself** (`_sandbox_import_table`: a module by its name, a Polars export from `polars`, anything else from the public module defining it), so a sandbox addition needs no table edit (`test_every_sandbox_name_gets_an_import_binding_the_same_object` pins each statement binds the sandbox's object; the FlowFrame export passes the code to `polars_code`, which runs it in the sandbox). Stored values — manual-input rows, a flow input's sample, the frame's own argument reprs — go through one renderer, `code_generator/literals.py::python_literal`: a NaN or infinity is written `float("nan")`, a date, time or zone gets its module import, and a decimal is `decimal.Decimal('…')` (never `Decimal(...)`, which the sandbox import `from polars import Decimal` would shadow). `native_handlers.value_literal` is the other thing: a pure-literal check (round-trips through `ast.literal_eval`, no imports) for settings values that must stay plain data.
- **Code export always chains a formula node's entries** — one `with_columns` call per active entry, in order, in both dialects (`code_generator/transform_handlers.py::_handle_formula` and the `FlowGraphToFlowFrameConverter` override); never a fused call for independent entries, never the `flowfile_formulas=[...]` list form for a whole node. A later entry may read a column an earlier one writes, and a chain shows that where a keyword form whose evaluation is silently sequential does not. Per entry the native expression is preferred and only that entry falls back (`simple_function_to_expr` / the single-entry `flowfile_formulas=` form). One-entry output is pinned by `tests/flowfile/test_formula_multi_entry.py::test_one_entry_emission_is_unchanged`: byte-identical to the pre-multi-entry baseline except the FlowFrame native row, which now pins an untyped entry (a typed one keeps the keyword form). This is the deliberate asymmetry with `flowfile_frame.with_columns`, which collapses independent expressions into ONE node (`formula_dependencies.entries_are_independent`, still used there only): a multi-entry node exports as a chain and re-imports as N single-entry nodes.
- **A formula node only travels in a share link with exactly one entry** (`share/compatibility.py::_formula_reason`) — WASM's `nodes_formula.py` reads `settings["function"]` alone and passes the frame through when it is absent, so a multi-entry node would run green-and-wrong in the browser.
- **Community-node installs are admin-gated** (`require_admin`, same reasoning as custom-node mounts — they land executable code install-wide) and tracked by a `community_receipts.json` sidecar living **inside** `user_defined_nodes/` next to the flat `<id>.py` files (never touch non-community files on uninstall). Consent + the client's sha256 pins are advisory; `installer.py` re-scans downloaded bytes and is authoritative — it also refuses blocklisted ids (410), yanked versions (410 `YANKED`), and `min_flowfile_version` mismatches (409 `INCOMPATIBLE_VERSION`); install never execs the node module (lazy exec at placement via `registry.ensure_class`). For offline/local UI work set `FLOWFILE_COMMUNITY_INDEX_URL` to a local `index.json` path (**fixture mode** — no GitHub repo needed).
- **In-app PR publishing must never surface a GitHub-domain failure as HTTP 401** — the frontend axios interceptor treats 401 as JWT expiry and would trigger a refresh/logout. `community_github.py` / `publish-pr` map GitHub errors to typed `error_code` payloads on non-401 codes instead (412 `GITHUB_NOT_CONNECTED`/`GITHUB_TOKEN_INVALID`, 410 `DEVICE_EXPIRED`/`DEVICE_DENIED`, 502 `GITHUB_API_ERROR`/`GITHUB_RATE_LIMITED`, 503 `GITHUB_NOT_CONFIGURED`, 409 `VERSION_NOT_INCREMENTED`). The device-flow client id comes from `settings.get_community_github_client_id` (env var → `.env` → baked `COMMUNITY_GITHUB_CLIENT_ID_DEFAULT`, so non-empty by default; an empty resolution ⇒ device flow disabled, PAT + bundle still work).
- **`enable_cdf=True` means "ensure enabled", not "on create".** `shared/delta_utils.write_delta` / `merge_into_delta` create a new table with the CDF property, and on an existing untracked table call `enable_change_data_feed` (a `SET TBLPROPERTIES` commit) *before* writing so the write lands above the floor — the catalog already enables first, so it is a no-op there. A cloud Delta path has no `CatalogTable.cdc_enabled_version`: its floor comes from `get_change_data_feed_floor`, which walks `DeltaTable.history()` for the newest `SET TBLPROPERTIES` that turned CDF on (a JSON-string `properties` parameter is decoded) and otherwise falls back to the oldest retained version, not a hardcoded `0`, because log cleanup can drop early commits.
- **Cloud nodes resolve their connection only through `flow_graph/cloud.py::_resolve_cloud_node_connection(settings, user_id, role)`** — path guard first (`validate_cloud_resource_path`; docker also refuses absolute local paths), then the own-first/group-granted connection or the ambient fallback (refused in docker). In docker a server-identity connection (`sharing.SERVER_IDENTITY_AUTH_METHODS`: `aws-cli`, `env_vars`, `iam_role`, `managed_identity`) is admin-only: `routes/cloud_connections.py` 422s a non-admin create/update and `db_connections.get_cloud_connection_schema` raises `CloudConnectionNotAllowedError` when the row's owner is not an admin (admin-owned rows, shared ones included, keep working). Never call the guard and `get_cloud_connection_settings` separately, and never put a strict validator on `CloudStorageSettings.resource_path`: `manage/io_flowfile.py` re-parses saved node settings with a bare `model_validate`, so an unconfigured cloud node would stop its whole flow from opening. The empty-path node description reads `Write (no path set) (…)` / `Read (no path set) (…)`.
- **Saved `aws-cli` connections read credentials from `cloud_storage_connections.aws_profile`** (blank/NULL ⇒ boto3's default chain), never from the connection's display name. Migration 033 adds the column **without a backfill** (maintainer decision — don't re-add a name-as-profile backfill); `db_connections._aws_profile_to_store` keeps the profile for `aws-cli` only, and `update_cloud_connection` keeps the stored profile when the caller omits `aws_profile`. Project export/import round-trips `aws_profile` (NULL for files written before it existed) and the session token as a `${secret:…}` placeholder. `aws_session_token` (access_key) is stored encrypted in `aws_session_token_id` and lives and dies with its key pair: a blank value on update keeps it only while the key ID and secret are unchanged; a new key ID or secret without a token, or another auth method, deletes it. It is deliberately **not** counted as a new credential by the sharing re-point guard.
- **With `FLOWFILE_COMPUTE_PROTOCOL` on, a cloud read's plan names its saved connection instead of carrying its credentials.** `CloudStorageReader.get_read_credentials` gives a Polars scan of a stored connection whose method holds a credential (S3 access key, IAM role, `aws-cli`; Azure key, SAS, service principal; GCS service account) the transport options only (`get_plan_storage_options`) and a `CredentialRefProvider(connection id, user id)` (`credential_ref` looks the id up by the same own-then-granted rule), so core resolves nothing to build it; whichever process runs the plan resolves it: a worker with its own catalog database, master key and AWS identity (a behaviour change for `aws-cli` and `iam_role`), core when core runs it, including the schema a reader takes at construction. `env_vars` and managed identity carry no provider; a connection not in the catalog, an `aws-cli` read with no saved connection, a GCS connection with an endpoint (gcsfs) and the flag off keep the `$ffsec$` provider. A remote worker therefore needs core's catalog: the same SQLite file co-located, the shared Postgres catalog on another host. The other plans that read a stored connection name it the same way: a cloud change read through `flow_graph/cloud.py::_cloud_change_scan_kwargs`, and every catalog scan of an object-storage namespace (table, SQL and change reads, a query virtual table's cloud sources, the SCD2 writer's output) through `CatalogStorageTarget.scan_kwargs`: with the flag on the target holds the namespace connection's `credential_ref` for the catalog owner and its `plan_storage_options`, and each call makes a new provider, so a target the reader resolved at wiring still resolves once per plan. Core's own reads of those tables keep the resolved `storage_options`, and the writes `worker_interface`.
