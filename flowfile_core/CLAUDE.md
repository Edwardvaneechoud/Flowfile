# CLAUDE.md - flowfile_core

Central FastAPI backend and DAG execution engine for Flowfile: manages flows as DAGs, runs node compute on Polars, hosts auth/catalog/secrets/AI/kernel subsystems, and offloads heavy work to `flowfile_worker`. Package-specific notes only; see the root `/CLAUDE.md` for monorepo-wide setup, build, lint, ports, and cross-package contracts.

## Role
- The hub of the system. The frontend (Tauri/web) and `flowfile`/`flowfile_frame` clients hit its REST API on **port 63578**; it calls `flowfile_worker` (63579) for compute, the kernel containers (Docker SDK) for sandboxed user code, and `flowfile_scheduler` for cron runs.
- App is `flowfile_core/main.py:app`; entry `flowfile_core.main:run` (poetry script `flowfile_core`). Also runs a saved flow in-process via `python -m flowfile_core.main --run-flow <path> --run-id <id> [--backend <id>]` (PyInstaller / CLI path; the run's backend is `--backend`, else a backend id saved as the flow's `execution_location`, else `FLOWFILE_COMPUTE_BACKEND` when set, else the worker embedded in this process (`local`, each job in a child, a pool of one: `registry.headless_run`, which both runners enter first and whose SIGTERM handler takes the children down with a cancelled run) whatever a saved `local`, `remote` or `auto` says; it becomes the process's default through `registry.set_default_override` and the flow runs `"remote"` on it, or `"local"` on `local`; drops UI-only `explore_data` nodes). `--run-id` is required.
- **Core compute contract:** core never materialises full LazyFrames for dataset memory. A flow's `execution_location` is `"auto"` or a backend id (`local`, `worker`, `worker:<name>`, an entry point's), `"remote"` the legacy alias of `"auto"` (a plain string in `schemas.py`; an id is not checked against the registry); with `FLOWFILE_COMPUTE_PROTOCOL` on a new flow's is `"auto"` and a file saved `local` or `remote` opens as `"auto"` (`schemas.loaded_execution_location`, applied to every format by `io_flowfile._load_flow_storage`, and in a process that serves by `POST /flow_settings` to the location it is posted, so such a core stores a posted `local` or `remote` as `"auto"`), with it off a new or `"auto"` location validates to `"local"` or `"remote"` and a file opens as saved. Each node's settings carry an `execution_location` too (`NodeBase`: `"auto"` by default, or a backend id), saved with the node (by `model_dump`, and by hand in the select, join, cross join, fuzzy match and output `to_yaml_dict`s) and among the AI planner's `_PLANNER_INJECTED_SETTINGS_FIELDS`; a run reads it only with an exchange store configured (`FLOWFILE_EXCHANGE_URI`, the mixed policy under Execution package), and otherwise every node of a run goes to the run context's backend but, with the protocol on, the Google Analytics reader, which its builder pins to the worker and which then runs, and submits its plan, under a context on the worker whatever the run's backend. A node's plan goes to the backend of the run's execution context (`ExecutionContext.for_flow`): the worker embedded in this process (`EmbeddedWorkerBackend`, the registry's `local`, its jobs run here, in a headless run in its children) for a `"local"` flow; the registry's default backend for an `"auto"` or `"remote"` one, the worker unless `FLOWFILE_COMPUTE_BACKEND` (or, unset, `FLOWFILE_OFFLOAD_TO_WORKER=0`) says `local`, never `local` in a process that serves, and the worker owns dataset memory in spawned subprocesses; the backend of that id for any other location; core ships plans and JSON. The bounded reads the engine makes of a plan (a count, a first row, an aggregate row, a pivot's distinct values) go through the current execution context's backend (`flow_data_engine/bounded.py`, see Key patterns) — don't add collects in core outside the sanctioned bounded reads.

## Layout
- `flowfile_core/main.py` — FastAPI app, lifespan (scheduler/kernel/local-model shutdown), CORS (Tauri origin regex + explicit dev/Docker origins), all router mounts, and the canvas notebook's runner, installed at import right after the notebook router (`install_notebook_runner()`), so every `TestClient(main.app)` has it without entering the lifespan. Its `RequestValidationError` handler answers FastAPI's own 422 shape (`{"detail": [{type, loc, msg, ctx}]}`) without each error's `input`, which repeats the request body (a token, a secret's value); single-file mode's worker routes, mounted on this app, answer through it too. Its `--run-flow` verb is checked at the top of the file, **before** the router imports and the import-time `storage.cleanup_directories()` sweep, so a run child never deletes cache/temp entries the live core still references; `multiprocessing.freeze_support()` runs before that check, as the worker's entry has it, so in a frozen build a multiprocessing child that re-enters the file (each job's child a run starts, the resource tracker) runs its own code and exits instead of starting a second serving core or running the flow again; the run verb lives in `flowfile_core/run_flow_cli.py` (`tests/test_run_flow_cli.py` pins that the sweep is skipped).

- `flowfile_core/change_feed.py` — the per-flow change feed behind `GET /editor/events` (`routes/routes.py`, next to `/editor/history_status/`): subscribes once to the bus events `flow_revision` (every `FlowGraph._bump_revision`: `graph` at the outermost `transaction` exit — stamped last, after `get_history_state`, and only when the persisted hash moved, so neither a failed nor a no-op request moves it — and for direct writes outside a transaction, successful undo/redo/`revert_if_top`; `run_started`/`run_ended` from `try_claim_run`/`release_run`; `saved` from `mark_as_saved`), `flow_closed` (`FlowfileHandler.delete_flow` and `evict_flow_by_path`) and `flow_rekeyed` (`rekey_flow`, a Save As: the old id's subscribers get `rekeyed` with `new_flow_id` and their stream ends), and hands them to per-flow asyncio queues with `call_soon_threadsafe` only, never blocking the mutating thread. `ClientOriginMiddleware` (pure ASGI, in `main.py`) reads `X-Flowfile-Client` into the `CLIENT_ORIGIN` ContextVar, which the threadpool route and the run's background task inherit, so every event names its origin. `subscribe(flow_id)` registers the queue and `_Subscriber.events(keepalive=)` yields `None` on an idle tick and ends on `closed`, `rekeyed` or `close_all()` (`stream()` composes the two); the route subscribes **before** it reads `flow.revision` for `hello`, so no change falls between. `close_all()` is called from `main._stop_server` (the `/shutdown` route, the parent-death watcher), from `main._Server.handle_exit` (uvicorn's `capture_signals` replaces the SIGINT/SIGTERM handlers while it serves, so `main.signal_handler` never sees them then) and the lifespan, because uvicorn waits for open connections before the lifespan shutdown. - `flowfile_core/flowfile/settings_validation.py` — conservative static check that node settings only reference existing input columns (per-node-type extractor registry + `validate_flow_settings`); served by `GET /flow/settings_validation`, gated per flow by `FlowSettings.validate_settings`. Flowfile formulas (formula node, advanced filter) are covered by walking polars_expr_transformer's parse tree for `pl.col` references. A second phase (`@_expression_probe` registry) asks whether the expression can run at all via `_extensions/real_time_interface.check_expression` — the runtime parser (`simple_function_to_expr`) applied to an **empty LazyFrame** built from the predicted schema (`filter()` for the advanced filter, mirroring `do_filter`, which is what enforces Boolean-ness), so a type error like `[n] + "a"` surfaces on the canvas without touching data; `${param}` refs are resolved first and skipped when undefined. **The registry's entry criterion is "columns whose absence makes the node *fail*", not "columns the node references"** — `select`, `dynamic_rename`, `multi_field_formula`, and the join-family select lists skip missing columns and keep running, so they deliberately have no extractor (`multi_field_formula` gets no expression probe either — its `[_Current*_]` placeholders are not real columns, so the probe would fail on flows that run; `run_flow` too: its parameter columns arrive on keyed handle `input-0`, which `main_inputs` cannot address). `tests/flowfile/test_settings_validation.py::test_warning_matches_runtime_behaviour` pins this by running each node type with a renamed-away column and asserting warn ⇔ failure, with a control run proving attribution — add a case there before adding an extractor. Warns only when the input schema is confidently known: no extractor (custom nodes, raw polars/SQL/python code), blocked or failed prediction, and empty schemas all stay silent — never add an extractor or probe that can false-positive.

- `flowfile_core/flowfile/converters/alteryx/` — Alteryx `.yxmd` importer: `yxmd_parser.py` (XML → tools/connections), `mappers.py` (per-tool node emitters), `expression.py`, `convert.py` (layout, wiring, validated `FlowfileData`), `report.py` (`ConversionReport`/`ToolReportRow`, statuses `converted|partial|commented|placeholder|out_of_scope|no_op|skipped`; every row also carries a required `reason` — why it has that status, from a closed vocabulary, so the numbers group without parsing English — and a `census_name`, the tool's identity for scope and grouping, which for a macro is its bare filename). **Formula translation is fail-closed** — an Alteryx expression is emitted only when it tokenizes, resolves every function through `FUNCTION_MAP` *and* round-trips the real Flowfile parser, otherwise the original text is preserved as a `//` comment above a safe stub (and an unsupported tool becomes a `polars_code` passthrough placeholder), never a best guess. **Every placeholder embeds the tool's original `<Configuration>` XML plus its Alteryx annotation as `#` comments**, so a node can be rebuilt without the source `.yxmd` (comments are stripped by `polars_code_parser` before execution, so they cost nothing at run time). Alteryx `NOT`/`!` translate to `not(...)`, but `IN` never does — Flowfile's `in` is substring containment, not set membership. Of Alteryx's three MD5 functions only **`MD5_UTF8` maps** (onto polars-expr-transformer's `md5()`, which hashes UTF-8 bytes); `MD5_ASCII` (narrow/Latin-1 bytes) and `MD5_UNICODE` (UTF-16LE) hash *different bytes* and stay rejected with a reason pointing at `MD5_UTF8` — Alteryx's own worked example `Md5_Ascii('Lá')`/`Md5_Unicode('Lá')`/`Md5_Utf8('Lá')` gives three different digests, pinned in `test_expression_translator.py`. `Base64Encode`/`Base64Decode` map onto `base64_encode()`/`base64_decode()` over the UTF-8 bytes of the text, without a caveat (identical for ASCII under any encoding). There is deliberately **no hex mapping**: Alteryx's `IntToHex`/`HexToNumber` are integer radix conversions, not the byte-level encodings `hex_encode()`/`hex_decode()` provide. Beyond the obvious 1:1 tools, `DynamicRename` maps onto the native `dynamic_rename` node (formula / first_row / prefix+suffix) or, for the right-input modes, is resolved at import time into a plain `select` when the name source is a readable Text Input; `MultiFieldFormula` maps onto the native `multi_field_formula` node, with the `[_CurrentField_]` / `[_CurrentFieldName_]` / `[_CurrentFieldType_]` placeholders preserved verbatim (they are the only `[_X_]` specials the translator accepts, via `try_translate(..., allowed_specials=...)`) and Alteryx's `FixedDecimal(size, scale)` output type stored as `Float64` with size and scale dropped. A **declared string output type is deliberately ignored** (the tool echoes the selection's own type into `OutputFieldType`, so a text-mode tool says `V_String` without meaning "stringify"): casting to text is a no-op when the expression already returns text and irreversible otherwise — Polars cannot cast text back to Boolean, so `price_paid.yxmd`'s `[_CurrentField_]='Y'` into a downstream Select retyping the column to `Bool` would break — and keeping the produced type is always recoverable. `RegEx` parse/match/replace becomes generated Polars code (rejected fail-closed when the pattern uses lookaround or backreferences, which Polars' regex engine lacks); and simple-mode `Filter` triples are rebuilt into an Alteryx expression and run back through the same translator. A headerless `Input Data` tool also emits a `select` renaming Polars' `column_1..N` to Alteryx's cached `Field_1..N`, without which every downstream reference to an Alteryx column name silently misses. `RecordID`, `CrossTab` (pivot; always `partial` because Alteryx underscores the new column names and Flowfile keeps raw values), `AppendFields` (cross_join), `RunningTotal` (window_functions `cum_sum`, `RunTot_<field>` names) and `Transpose` (unpivot chained into a `variable/value` → `Name/Value` rename select) also map onto native nodes; `Switch`, `ReplaceChar` (nested literal `replace()`s) and `DateTimeFirstOfMonth`/`LastOfMonth` translate in the formula dialect, and the emitter parenthesizes compound `=` operands because polars_expr_transformer gives `=` maximum binding power. Macro tools carry no plugin name (`tool_name` is empty), so `get_mapper` dispatches them through `MACRO_MAPPERS`, keyed on the `EngineSettings Macro` filename basename; the Data Cleansing macro (`Cleanse.yxmc`) maps onto the native `data_cleansing` node — its config is the macro's flat question-value list (`<Value name="Check Box (N)">`), whose widget ids are matched by name and fail closed on any missing or unrecognized entry rather than guessing by position — and the Count Records macro (`CountRecords.yxmc`) onto `record_count` chained into a select that renames `number_of_records` to Alteryx's `Count` (Int64). Alteryx **Comment** tools (`AlteryxGuiToolkit.TextBox`, parsed into `AlteryxWorkflow.text_boxes` with their size) become canvas **comments** (`FlowfileData.comments`) positioned on the same scaled origin as the tools; only the text travels (colour, font and shape are dropped), and an empty text box — Alteryx's decorative background band — is reported `skipped` rather than imported blank. `tool_identity.py` is the canonical tool key (`tool_key`/`is_official`; see the telemetry gotcha) stamped on every `ToolReportRow.alteryx_tool_key`; `flowfile/node_requests.py` (not converter-specific) proxies the open node-request GitHub issues for both labels — `alteryx-node-request` (title convention `[Alteryx node] <key>`, `.github/ISSUE_TEMPLATE/alteryx_node_request.yml`) and the free-form `node-request` (`node_request.yml`) — cached in-process for the community TTL (a failure is cached for 60 s as empty, never an error). `GET /node_requests` (router `routes/node_requests.py`) lists them for the sidebar's Request-a-node dialog (title search + upvote links + prefilled new issue); `GET /converters/alteryx/node_requests` derives the key→URL map so the import dialog can link a placeholder row to its open request. ## Key patterns & conventions
- **Router wiring is centralized:** add endpoints by including the router in `main.py` (order/prefixes there are load-bearing — e.g. `ai_admin_router` mounts on `/system`, not `/ai`, so admins can flip the gate). Most editor routes carry `Depends(get_current_active_user)`; `public_router` and `flow_api.data_router` are API-key-authenticated (`verify_api_key`) instead.
- **In-memory flows are per-session; resolve them for the caller.** A flow id is not a secret (the flow's file stores it and `import_flow` reuses it), so every logged-in route that names an open flow resolves it with `routes.get_flow_or_404(flow_id, current_user)` (AI/ML/log routes call `flow_file_handler.get_flow(flow_id, current_user.id)` and keep their own status codes); another user's flow answers exactly like a missing one. `get_flow(flow_id)` without a user is unscoped — internal callers and lookups after a scoped check only. `import_flow` gives the flow a fresh id (and a fresh per-id `FlowLogger`, which the `flow_id` setter does not rebind) when its stored id is open in another user's session, and `register_flow` refuses a taken id without evicting the holder. `tests/sharing/test_flow_session_isolation.py` builds its route list from the live app and fails on any unscoped lookup of another user's flow; exempt a route there, with a reason, only when its `flow_id` does not name an in-memory flow (catalog registration ids, kernel namespace keys, the token-signed `/raw_logs` sink).
- **AI gate:** the whole `/ai/*` router is gated by `FEATURE_FLAG_AI` (live-mutable `MutableBool` in `settings.py`; `ai/feature_flag.py` `is_ai_enabled`/`require_ai_enabled`, returns 503 when off). The `/system` admin route flips it without restart.
- **Keep the `ai` package litellm-import-free at module level.** Every `import litellm` is lazy (inside functions): `ai/providers/_litellm_base.py` and `ai/scheduler.py` (`from litellm import exceptions`). `ai/__init__.py` `setdefault`s `LITELLM_LOCAL_MODEL_COST_MAP=True` before any lazy import. Re-adding an eager litellm import breaks `test_classification`/`test_dry_run` lazy-contract tests. BYOK key wiring lives in `ai/byok.py` (reads `ai/credentials.py`, sets provider env vars litellm picks up); providers registered in `ai/providers/registry.py`.
- **Secrets format:** `encrypt_secret(secret_value, user_id)` → `$ffsec$1$<user_id>$<fernet_token>`; key is `HKDF-SHA256(master_key, info="user-<id>")`. The embedded user_id lets the worker decrypt without user context; legacy raw-Fernet tokens still decrypt via the `user_id` param.
- **API-key hashing is deliberate SHA-256** (`auth/api_key.py:hash_api_key`) — 256-bit random tokens, not passwords; don't "upgrade" to a KDF (the CodeQL weak-hash alert here is a known false positive). Passwords use bcrypt (`settings.PWD_CONTEXT`).
- **Kernels:** `kernel/manager.py` allocates host ports from **19000–19999** (`_BASE_PORT=19000`, `_PORT_RANGE=1000`) per container; image flavours (`ImageFlavour.BASE/ML/LITE/NOTEBOOK/CUSTOM`) resolve their package inventory from `kernel/kernel_image_manifest.json`, generated from `kernel_runtime/{pyproject.toml,poetry.lock,Dockerfile}` by `tools/generate_kernel_manifest.py` and read package-relative in `kernel/flavours.py`. Image *tags* live in `kernel/images.py` (docker-free, so `matching.py` can read them without pulling in the docker SDK); `manager.py` re-exports them. **Creating a kernel pulls a missing image itself**: `create_kernel` runs `_ensure_image(base_image)` in `POST /kernels/`, and `_build_derived_image` calls it too, so a package edit pulls as well. It is an inline `_do_pull` (refs split by `docker.utils.parse_repository_tag`, so registry ports and `@sha256` digests survive) that waits on a `start_image_pull` already in flight and records the same `pulling`/`error:<msg>` pull state, so `docker-status` reports it like a background pull; a failed pull is the route's 409 `Failed to prepare kernel image: …` and the kernel is never registered. Starting a kernel pulls a missing base image the same way (the pin moves with an app release for the notebook flavour), and a derived image is reused only while its `flowfile_base_image` label names today's base — otherwise it is rebuilt on the new one. **How a kernel reaches core is `kernel/urls.py::core_base_url` and nowhere else** — both `_build_kernel_env`'s `FLOWFILE_CORE_URL` and `execution.py`'s `/raw_logs` callback go through it, keyed on `_docker_network` (the kernel resolves core by service name only when it was joined to core's network) and using `settings.SERVER_PORT`, never a literal. Two independent constructions with a hardcoded `63578` in one of them is how the desktop app, which port-scans for a free pair, ended up sending a kernel's API callbacks to a different process than its log callbacks. **Startup GC is fail-closed and ownership-scoped.** `_restore_kernels_from_db` returns whether the registry is authoritative; when it isn't, `__init__` skips the orphan-container reap and the derived-image GC entirely (adoption still runs — it only adds knowledge). One swallowed DB error used to leave `_kernels` empty and the GC passes read that as "nothing should exist", destroying every container and image. Containers now carry ownership labels: `flowfile_core_instance` (which install, stable) and `flowfile_core_runtime` (which *process*, per-boot). Reaping needs the install label plus a 10-minute age grace; `shutdown_all` stops only kernels in `_started_here` — the DB-shared registry also lists kernels another core started, and tearing those down is how quitting the desktop app killed a dev core's kernels. `FLOWFILE_KERNEL_GC=0` disables reclamation outright. Shutdown duty transfers on adoption when the owning pid is gone (`_claims_ownership`, reusing `shared/run_completion._pid_is_alive` — `os.kill(pid, 0)` kills on Windows, so never probe by hand), so a hard-killed core doesn't leak its containers forever while a *live* owner keeps its own. Pre-label containers and pids recycled across a reboot leak instead; that direction only leaks, never kills another core's kernel (`make clean_kernels` is the manual sweep). The `get_kernel_manager` singleton is lock-guarded and warmed by a best-effort daemon thread at startup (`FLOWFILE_KERNEL_WARMUP`, default on; forced off in `tests/conftest.py` so TestClient lifespans never touch Docker). `KernelManager` construction first probes the daemon with a short-timeout client (`_DOCKER_PROBE_TIMEOUT_SECONDS`) and the kernel routes fetch the manager via `asyncio.to_thread` — never call `get_kernel_manager()` or `docker.from_env()` directly from an async handler, because a hung daemon then freezes every request in core (`docker.from_env()` negotiates the API version under the SDK's 60 s read timeout, on the event loop). Starts are **single-flighted** per kernel (`_start_flights`) and container creation converges on name conflicts via a bounded create-or-adopt loop (`_create_or_adopt_container`: adopt the holder if it runs the desired image ID, else replace it). Execution is **serialised per kernel** (`_exec_locks`, one cell at a time) because the runtime execs cells into a shared namespace in one interpreter — concurrent cells race imports; `/interrupt` deliberately takes no locks so a running cell can always be cancelled. **Cancellation is addressed to an execution, never to a kernel**: every `ExecuteRequest` carries a server-minted `exec_token` (`build_execute_request` for flow runs, `execute_sync` for everything else; the `/execute[_cell]` routes blank any client-supplied value), `_active_execs[kernel_id]` records which token holds the exec lock, and `interrupt_execution_sync(kernel_id, exec_token)` refuses to fire unless that token is the one running. Without this a flow queued behind another flow on a shared kernel cancels the *other* flow's cell — `FlowNode.cancel` must always pass its own token, and the kernel's `/interrupt` binds the token to that cell's generation (a token whose cell already finished interrupts nothing rather than falling back to the newest cell). **Dependency matching** (`kernel/matching.py`, `packaging`-based, pure): `POST /kernels/match` (and the digest form `POST /kernels/match/batch` powering list-view readiness badges) ranks the caller's kernels against a custom node's pip specs (version-aware; a kernel "provides" = manifest packages for its flavour ∪ requested `packages` names ∪ `resolved_packages`) and returns a create-from-spec `KernelConfig` seed (ML flavour inferred from dep names, slugified collision-free id); it **degrades to DB-persisted kernels when Docker is down** — no 503. At run time `flow_graph/builders/custom_nodes.py::_execute_on_kernel` pre-checks a kernel-env custom node's deps (`verify_kernel_for_node` → typed `KernelDependencyError`); only *provable* mismatches block — unverified versions, unknowable images, and invalid specs never do.
  **A kernel whose contents can't be enumerated is `level="unknown"`, never `"full"`.** That covers a custom image, a flavour repointed by `FLOWFILE_KERNEL_IMAGE_*` to a different release than the manifest describes, and a missing manifest. Collapsing that into `full` is what made every packaged install report "✓ has all packages" for kernels that had none, so keep `unknown` distinct from `unverified` (which means the image *was* enumerated and the name was found, but the version or extras aren't provable). `tests/test_kernel_packaging_gate.py` keeps the missing-manifest case unreachable in shipped artifacts; `tests/test_kernel_dependency_gate.py` (`-m kernel`) checks the manifest against a real `pip list` inside the image.

- **Undo/redo: one transaction per mutation, one graph builder.** Every editor mutation route runs in `routes.edit_flow` → `FlowGraph.transaction(label, action_type)`: it holds the per-flow edit lock (`FlowGraph.edit_lock()` is the only way to take `_edit_lock`; a bounded wait answers 409, and a contended wait on the event loop is logged as an error and raised under `TESTING`, so call from sync routes or `asyncio.to_thread`), snapshots before and after, records **at most one** step and only when `history_schema.in_scope_hash` changed, and on any exception restores the pre-request graph without touching the stacks. Nested recording (`@with_history_capture` on every `add_*`, `_execute_with_history`) records nothing inside a transaction or restore. A multi-part gesture is one `POST /editor/apply_operations/` (`schemas.ApplyOperationsRequest`, dispatched to the single-op route functions; the batch-only `insert_on_edge` splices a node into an edge through `FlowNode.replace_input_source`, keeping the target's input slot and position — delete + connect would renumber `input_df_N` and reorder a union). Undo/redo take `edit_lock()` directly, since an outer transaction would record the restore as a step. `io_flowfile.populate_graph_from_flow_information` (inside `FlowGraph.rebuilding()`) is the **single builder** for `open_flow` and `restore_from_snapshot`, so `snapshot(build(s)) == s` (`tests/flowfile/test_history_invariants.py`); opening a flow is build plus empty history. **Scope** is nodes, groups and comments: restore keeps the live `FlowSettings` and identity, `/flow_settings` keeps `_SERVER_OWNED_FLOW_SETTINGS`, and settings saves keep the server-owned `pos_x`/`pos_y`/`group_id` (`keep_server_owned_layout`). **Dirty** is `persisted_hash(current) != persisted_hash(saved)`, refreshed after every transaction, undo, redo and save (before the first save, non-empty content counts as dirty). **Reads and runs never write settings:** `get_node_data` runs setting generators/updators on a deep copy (join/cross_join/filter proposals, Filter's derived `advanced_filter`, Select's `is_available`), `_func`s reconcile on a per-call copy, and `NodeData.is_setup` reports the live node's state, which is how the drawer tells a never-configured node from a proposal. - **Settings are `MutableBool`** so they toggle live: `SINGLE_FILE_MODE`, `OFFLOAD_TO_WORKER`, `FEATURE_FLAG_AI`, `FLOWFILE_AI_LOG_PROMPTS[_SCRUB]`, `FLOWFILE_COMPUTE_PROTOCOL`.
- **Conditional execution is a local trigger rule, never a closure.** `flowfile/util/skip_rules.py` classifies every node from its *immediate* inputs in topological order (`classify_graph` for the plan, `classify_from_inputs` per stage in `_execute_stages`); `node_skipper` and `get_all_dependent_nodes()` are thin wrappers over it. **ALL** is the rule for every node (an error-ish input ⇒ `SKIPPED_ERROR`, else a deliberately-skipped input ⇒ `SKIPPED_DELIBERATE`); **ANY** is `union` **only** (`ANY_INPUT_NODE_TYPES`) — the other multi-input types address inputs positionally (`input_df_1..N`), so eliding one would silently renumber the rest. Failure never inherits ANY: a failed branch must not become "half the data written successfully". The two skip *causes* must stay distinct — error-ish (misconfiguration, failure, cancellation) blocks everything downstream as before, while **deliberate** skips originate only from gates routing a side dead and are a *successful* outcome: `NodeResult(success=True, skipped=True)` rows (`_record_deliberate_skips`) so the run stays green and `nodes_completed` still reaches `number_of_nodes`, and `_run_post_execution_callbacks` treats them as complete so a Kafka source upstream of a closed gate still commits its offsets (it only logs a warning when a gated-off *output* node is involved). Gate timing is split: **parameter**-mode conditions resolve before the run (`_evaluate_gate_conditions` → `closed_gate_handles` → `compute_execution_plan`; an unevaluatable condition is left *open* so it fails visibly at the node instead of silently picking a branch), **formula** conditions (a flowfile-formula row predicate; open iff ≥1 row matches, checked against the control input when connected else the gate's own data input, `${param}` refs resolved with the run's params) are decided in the stage loop after the gate executes (a bounded `filter().head(1)` in `_gate_formula_matches`, collected in core, or with `FLOWFILE_COMPUTE_PROTOCOL` on read through `bounded.head_rows` on the backend that holds the gate's source's result for its current setup, else on the run's backend, or outside a run (`ff.Gate.is_open`) on the gate's graph's; folded into `closed_gate_handles`) — which is why `executor.py` gives formula gates an unconditional **always-run** decision alongside output/`run_flow` nodes: the checked data can change without any hash changing. Legacy `control_input`/`invert` gate settings migrate on load (`GateInput._migrate_legacy_shape`: source → formula; inverted parameter operators flip to their complement). Gate closure is **per output handle**: an opt-in `NodeGate.else_output` gives the gate a second exit (then=output-0 / else=output-1; `output_names` property, filter-split pattern — no NamedOutputs, both handles serve the passthrough via `get_output`'s fallback), and `closed_gate_handles: dict[gate_id, frozenset[dead handles]]` (`dead_gate_handles()` in skip_rules: open+else→{output-1}, closed+else→{output-0}, closed+no-else→BOTH so a stale else edge left by toggling the option off never leaks); `effective_input_status` takes the edge's source handle (from `_slot_input_pairs`/`_input_output_handles`), a FAILED gate still kills every handle, and the union's `_skipped_input_ids_this_run` is (source id, handle)-keyed. Known limitation: `_input_output_handles` keys one handle per source, so both exits of one gate cannot wire into the SAME consumer (pre-existing filter-split limitation). A routed gate is itself `RUN`; only its dead-handle consumers read it as skipped. Two cache invariants make gate flips safe: (1) **a node that did not execute this run has not run** — every skipped node's `has_run_with_current_setup` / `has_completed_last_run` are cleared on both `node_stats` and `_execution_state`, or dev-mode serves the previous run's frame; (2) an ANY-rule node's **surviving-input signature** is tracked in `FlowGraph._any_input_liveness` and a change calls `invalidate_cache()`, because the node hash folds only settings + input hashes and would otherwise serve the previous run's partial concat (also from the worker's `cache_results` lookup). A gated-off union input is **dropped** — the union outputs only the surviving branches, so a dead branch's unique columns are simply absent from the output (edit-time schema prediction stays gate-blind and still shows the union of all branches). Gate-blind callers (code export, single-node fetch validation) omit `closed_gate_handles` and deliberately plan as if every gate were fully open. Only the Polars export emits gates as real if-blocks from the shared base machinery (condition atoms are signed `(gate_id, needs_open)` pairs — else-side consumers render `if not (...)`, except that adjacent blocks whose conditions are one gate's exactly-complementary singleton pair fuse into a real `if`/`else` via `_conds_are_complementary`; shared prefixes, different gates, and multi-atom sets never fuse because the else of `if P and g` is not `P and not g`) — never as `df.gate(...)` calls, which would be silently ignored by the rebuilt graph's pull-based execution; unions render as guarded list-appends — each branch appends its frame to a list under its `if` guard and the union concatenates the list, so a gated-off branch simply isn't in it — except a two-input union whose guards are exactly that complementary pair, which collapses to an `if`/`else` assignment, and the all-guarded empty-frame fallback (`if not <list>:`) is emitted only when no complementary pair proves the list non-empty (independent gates); pre-initialized empty stand-ins survive only for gated return values (`_empty_frame_schema_expr`); the formula row-probe helper gets its frame via `_gate_probe_expr`, with the `pl` import registered eagerly in `_compute_gate_conditions` because imports serialize before the gated body renders. The FlowFrame and project exports (the `ff` dialect) skip that machinery (`_compute_gate_conditions` is a no-op there) and place `ff.Gate(...)`, consumers reading `.then`/`.otherwise` — the same statements the canvas notebook shows as fused cells.
- **Catalog data freshness is version-addressed, never TTL'd.** Three coordinated mechanisms keep every surface current when a Delta table changes (including out-of-band writes): (1) `FlowGraph._refresh_catalog_reader_freshness` runs at every `run_graph` start — it probes live Delta versions (`catalog/delta_utils.py::get_live_delta_version`, cloud-aware) against the fingerprint stored in `NodeExecutionState.source_version_info` and calls `FlowNode.invalidate_cache()` on drift, which bumps `_cache_epoch` → rotates the node hash → defeats both the Development-mode skip and the explicit `cache_results` worker lookup, cascading downstream (pinned `delta_version` readers are never probed — deliberate time travel; readers over non-optimized virtuals invalidate every run, like `run_flow`). (2) Viz session keys (`catalog/services/visualizations.py`) fold live versions in: `tbl:{id}:v{version}`, SQL digests include referenced-table versions, fvt keys embed the snapshot filename+mtime — a write rotates the key and the stale worker child idles out (no push-evict; the endpoint exists for ops only). (3) Virtual-table resolution: `check_source_versions_current(None)` is **fail-closed** (no fingerprint ⇒ stale ⇒ re-run the producer); `_collect_source_table_versions` is **complete-or-nothing** (any unfingerprintable source ⇒ `None`; a flow with zero catalog sources stamps `"[]"` — provably complete, keeps plan replay); callers key the worker IPC cache via `fresh_versions_hash()` **after** resolution (identity-map-bypassing `get_table_fresh`), and the worker names that cache by `(table_id, plan_bytes, versions_hash)` with `NO_VERSIONS_HASH` always rebuilding. When touching any of these, keep the invariant: a cache key must change whenever the data it names can have changed.

  - **No location branch.** A site that needs compute calls `FlowNode.run_op(current_context(graph).backend, kind, op_payload(x), job_id=x.job_id)` (a plain plan goes through `_do_execute`'s `submit`) and turns the refs into engines the same way for both backends: `plan_for` with `ref.schema` and `ref.row_count`, a deferred ref released at once, a stored one kept held because the engine's plan scans its file. The registry is the one module outside `configs/settings.py` that reads `OFFLOAD_TO_WORKER` or `WORKER_URL`; `tests/flowfile/execution/test_inline_location_branches.py` fails any other reader and any inline `execution_location` compare. The two pins are the exceptions: the Google Analytics reader runs on the worker, and a custom node whose class has no node file runs on `local`, whatever the flow says.
  - **One payload for both backends.** Credentials enter a payload or a plan only as `$ffsec$` ciphertext or a `CredentialRef`, and `WorkerBackend` sends a write's cloud connection to a backend whose cached verdict declares `credential_resolution: ambient` with its credential fields `None` (`backends/worker.py::_transport_only`, in `_cloud_write_settings` and `_storage_payload`); the in-process hooks a payload carries (a cancel check, a node logger, the Kafka consumer, a placed custom-node instance) are core's, and no backend reads them. Job ids come from the node hash, so a rerun's job replaces the last; a schema prediction runs as `<job id>-schema` and is released once its columns are read.
  - **No plan is resolved in core.** With `FLOWFILE_COMPUTE_PROTOCOL` on a node function builds its output engine with the schema `_derived_schema` resolves over an empty frame of each input's cached schema (`FlowDataEngine.polars_schema()` answers from the cache; where a bounded read names the columns, over the steps after it), and a new node function does the same. `test_serving_app_ratchet.py` fails a `.collect(` over a `plan_for` leaf in core or the pip server's app. The flag is read per call, and every change on this path works in both flag states: with it off core uses the worker's task routes and reads its files over the shared disk.
  - **A node owns what it minted.** `results.result_ref`, the outputs stored beside it (`_stored_outputs`) and its operations' outputs (`_operation_refs`) are released together by `FlowNode.release_result`: before a rerun under another hash or backend, on `delete_node`, on `close_flow` (`delete_flow`, `evict_flow_by_path`, an in-place `import_flow`, the published-flow runner and both headless runners), and when `_store_other_outputs` fails. A Run Flow node adopts its child's stored results (`adopt_results`), and a preview fetch's cache reset sends the nodes downstream back to not-run (`drop_downstream_results`). A release that fails is logged and the reference dropped (`_release_or_drop`), so a close or a run's end always completes; a held result lives in core, so no cache survives a restart.
  - **A core that serves computes on its worker.** `main.run` calls `registry.mark_serving()` (the desktop sidecar, the Docker image, `flowfile run core`, the pip server; not a `--run-flow` child, a library, a test or a `TestClient(main.app)`), and there the default backend is never `local` and `local` runs no node (`placement.SERVING_LOCAL`). A headless runner sets the default override to its run's backend; `tests/conftest.py`'s backend guard restores it and fails a test that leaves it set.
  - **Placement ends a run before a node starts.** A refused node is one failed `NodeResult` (`cannot run on backend "<id>": <reason>`, `compute_error` `"Refusal"`), and nothing is prepared, executed, skipped or committed. An unreachable backend's nodes fail with its `ComputeUnavailable` when they run and never run elsewhere; `NodeResult.compute_error` names the typed class that failed a row. `place` reads resolved deep copies of the settings, so `preview_placement()` is safe beside an edit or a run.
  - **Catalog work goes where the data is.** The catalog writer names its table by identity (`CatalogTableIdentity`), the compute answers where it wrote, and an answer that is not the record's location fails the write before anything is registered or deleted. The catalog services go to the worker when the context's backend is not `local` (`uses_worker()`), and a worker that cannot be reached is `ComputeUnavailable` (503), never a read in core.
  - **The wire.** Every kind but the three Delta writes and `viz_session` goes over `POST /v1/ops/<kind>`; `polars_code` and `sql_query` have no task route, so they go there in both flag states. A `WorkerBackend`'s token is checked with `is_header_value` before any client sees it (`_sendable_token`, `TOKEN_RULE`): a refused one fails the call naming the backend, never the token, since `http.client` and `websockets` would print it. `result_file(ref)` and `task_result(handle)` are `WorkerBackend`'s own, not the protocol's.
- **Typed compute errors.** `flowfile/execution/errors.py` is the typed error family for talking to compute (`ComputeError` and its subclasses). `ComputeUnavailable(message, *, backend_id=None)` ends a refused connection's message with what to do once: `Is backend "<backend_id>" running? Start it, or check the Backends page.` when it has an id, else `Is the compute backend running? Start it, or check the Backends page.`; a message that already ends with the advice is read as it is, so an error rebuilt from a run report row's text (`api_runner._first_compute_error`, made with no id) reads it as the row does. With `FLOWFILE_COMPUTE_PROTOCOL` on or off, `WorkerBackend` makes every `ComputeUnavailable` for a worker it cannot reach with its own id (`_run`'s too, for a task-route request that fails after the gate passed) and hands the id to the handshake gate from its `/v1` requests and its `/v1` submit socket, which names it on the error the gate raises; the task-route fetchers and trigger functions enter the gate with a URL only, and the gate's error then names the backend that owns the URL (`handshake.owns`), none for a URL no backend was made on. `subprocess_operations.results_exists` raises `ComputeUnavailable` (naming the worker URL) when the worker cannot be reached; `False` means only that the worker answered the result is not there. The cache check asks only about a stored (`"materialised"`) result the node holds under its current hash on the run's backend (`FlowNode.held_result`, then `exists`); a node holding none has no cache, and a held deferred plan is no cache; a `cache_results` node in local mode is stored by the embedded worker in both flag states, so its stored result under core's cache directory is its cache, as on the worker beside core, and the worker beside core is never asked. `NodeExecutor.execute` records any `ComputeError` raised while deciding through the normal failure path (`_prepare_for_execution` + `_handle_error`): the node fails with the typed message, is never rerun in core and never read as a cache miss, and a cached node whose last run failed reruns past its cache, which clears the error and lets `FlowNode._do_execute` read the stored result back. Schema prediction (`FlowNode.get_predicted_resulting_data`) treats an unreachable worker as "needs run" with a warning, so it never fails on an outage. A worker that cannot run a task fails it typed through `errors.worker_failure`, using the worker's `error_kind`, which `BaseFetcher.error_kind` carries: a plan the worker cannot load fails the node with `PlanRejected` (so does the worker's time-limit kill, which it labels the same way), a killed child with `TaskFailed`, and nothing continues in core. The published data API answers 503 when the worker is unreachable and 500 for other compute errors, with generic detail on the public `/api/data/{slug}` route and the typed message on the owner's `/test` route. With `FLOWFILE_COMPUTE_PROTOCOL` on, a published run that fails raises the typed error of its first failed node, rebuilt from that node's run report row (`compute_error` and its text, `api_runner._first_compute_error`), so a worker unreachable when the run starts answers 503 like one gone before the final read; a failed row that names no compute error (the node's own failure, a placement refusal) answers 500, as every failed run does with the flag off.
- **Bounded reads.** `flow_data_engine/bounded.py` is how the engine reads a plan without holding it: `count_rows`, `head_rows` (an Arrow table), `single_row` (a dict of `pl.DataFrame.row` values; `ValueError` with the caller's message on an empty plan) and `unique_values` (the distinct values of a one-column plan, sorted, null first, at most `limit`, in the column's dtype; given the column's name, as `do_pivot` and `pre_calculate_pivot_schema` give it, it does not resolve the plan's schema) each submit the plan under a fresh `bounded_<hex>` id with `DEFERRED_HINTS` (no materialisation, no inline sample, so it stays deferred on every backend), make one `count` or `sample` and release it in a `finally`, filed under flow and node `-1`. A backend failure propagates as its `ComputeError`; nothing falls back to computing in core. The engine sites read the current execution context's backend: `FlowDataEngine.get_number_of_records(backend=)` (the count `get_sample`'s evenly spaced sample needs; without a backend it still counts in process), `_peek_first_row_as_dict` (dynamic rename `first_row`), `_fetch_null_profile` (data cleansing `remove_null_columns`), `do_pivot` and `schema_callbacks.pre_calculate_pivot_schema` (the first 200 distinct pivot values, cast to text in core), and `_calculate_schema` → `utils.calculate_schema` (the schema with `describe`-style statistics as one aggregate row over the first million rows, built in core; the worker's `calculate_schema` task is no longer called). Column statistics (`column_stats.compute_column_stats(engine, column, backend)`) run on the backend `FlowNode.get_column_stats` is given, by default, with `FLOWFILE_COMPUTE_PROTOCOL` on, the backend that holds the output's result (`FlowNode.result_backend`), else the backend of the node's graph's context (`_in_execution_context`; outside a run the flow's own, the default backend for a node with no graph), and with it off `current_context().backend`, which outside a run is the default backend, not the flow's, so a local node's stats aggregate on the worker when one is configured (`/node/column_stats` passes none); a failed full query retries counts-only on the same backend, and a `ComputeError` there is `ColumnStatsUnavailable` (409). With `FLOWFILE_COMPUTE_PROTOCOL` on, the column's dtype comes from the engine's cached schema, never from resolving its plan, and three more readers of a node's result go through a backend: the formula editor's preview row (`extensions._first_preview_row`: the node's cached sample or `sample(ref, 1)` on the backend that holds its reference, a secondary output's row through `head_rows` on that backend), `/node/data/export` (`head_rows` of the first `limit` rows on the backend that holds the node's result, else the flow's, its schema checks from the engine's cached schema, the CSV written by that backend's `file_write`) and the preview of an output of a multi-output node (`FlowNode.get_table_example` with an `output_handle`: the default output's rows from the node's cached sample, any other output's from `sample` of the result the node holds for it (`FlowNode.held_output`: the output it stored beside its result, else its operation's output by handle or, one per handle as a random split's, by position) on the backend that holds it, and those of an output with none, and the default's when no sample was kept, through `head_rows` of the output's plan on the backend that holds the node's reference, not cached), so none of them opens a backend's stored file in core. Outside a run a node's function runs in its graph's context: `add_node_step` gives the node `_execution_context_getter` (`current_context(graph)`), which `FlowNode` enters around its function in `get_resulting_data` and `_predicted_data_getter`, so a FlowFrame's build-time read of a local graph reads on the worker embedded in this process and a remote graph's on the default backend; a node a builder creates itself has no getter and its reads take the context they are called in. Tests: `tests/flowfile/execution/test_bounded.py`. `tests/flowfile/execution/conformance/` runs the protocol's guarantees over every backend in its `conftest.BACKENDS` (the worker embedded in the test process with its jobs run in process, under its own id `local`, and the session worker): bounded rows, a backend refusing another backend's results, every table result carrying the schema of its rows, a blob held as a copy of its bytes, copied out to a `file://` URI and never planned over, sampled or counted (on the worker with the protocol flag on only), a result core requires materialised and a wide one stored as the backend's policy says, a result exported to a URI and imported back as a deferred result of the same backend, with `export` refusing another backend's results, `run_op` refusing exactly the kinds `capabilities().operations` leaves out, and typed errors (out of reach, released, other versions).
- **Worker handshake.** The transport holds no worker URL: every function and fetcher in `subprocess_operations` (and `streaming.streaming_start`) takes `worker_url`, the worker's base URL, from its caller, `WorkerBackend` its own `url` and every other caller (the catalog services, the REST "Fetch sample" route, the published-flow runner, the custom-node dry run, the `/system/worker_pool` proxy, `FlowDataEngine`'s worker helpers, the startup print) `registry.worker_url()`; a `_worker_session` call names it and the route on it (`_worker_session.get("/status/x", worker_url=...)`). Every such request and every `/ws/submit` and `/v1/ws/submit` connect first calls `subprocess_operations/handshake.py::ensure_handshake(worker_url, *, backend_id=None)` with that URL, and `WorkerBackend`'s `/v1` requests (`_worker_session.request(..., backend_id=...)`) and `/v1` submit socket with its id too, which the gate's `ComputeUnavailable` names (the given id, else the backend that owns the URL, none for a stand-in). The gate passes by the verdict of a backend: the one last checked under the id when it runs on that URL, else the `WorkerBackend` that owns the URL (`handshake.owns`, called by every `WorkerBackend.__init__`; one that signs with the process token, as a URL-only call does, keeps the URL from one with a token of its own), else a `WorkerBackend` made there to stand in. `handshake.verify(backend)` is one check for every backend kind, through its interface only: `capabilities()` compared with `local_capabilities()`, then each probe plan run as an ordinary job, `submit` with the cheapest hints and `preview_rows=1` under result id `handshake-<probe>-<hex>` as flow and node `-1`, `sample` when no sample came inline, `release` in a `finally`; the probes are one empty-frame plan per expression plugin and one carrying a trivial Python function (`placement.PYTHON_FUNCTIONS`, `"python"`). Its `Verdict` (`id`, `ok`, `core`, `backend`, `differences`, `offered`, `absent`, `error`) is cached per backend instance and kept as the last of its id (`last_verdict`); `verdict_for` answers a cached passing verdict and checks otherwise, the calls that find a backend unchecked at once sharing one check (single-flight per backend), so a refused one is checked again on its next use, and `ensure_verdict` raises `VersionMismatch(verdict.error)` for a refused one. `protocol_version` (the worker contract), `polars_version` and `polars_runtime` refuse the backend whole (`Backend "<id>" does not match core (<field>: core <a>, backend <b>; …)`, nothing sent and nothing run in core instead), and so does `credential_resolution: ambient` while `FLOWFILE_COMPUTE_PROTOCOL` is off (`handshake.ambient_refusal`, naming the flag: with it off core's plans carry `$ffsec$` credentials and placement's ambient rule does not run; a 404 on `GET /capabilities` with the flag off also names the flag as a cause, since a `/v1`-only backend answers it); `app_version` is reported in `backend` and compared nowhere, so workers of another release that speak core's contract run; `python_version` is compared and listed in `differences` but the Python probe decides, a failure absent under `"python"`; a `PLUGIN_PACKAGES` package core has is absent where the backend lacks it, has another version or (an expression plugin) its probe fails, a package with no probe plan decided by its version alone; `platform` and `plugin_libs` are reported in `backend`, compared nowhere; `offered` is `backend` with `plugins` cut to what it offers. While the probes run, the comparison's verdict stands, so the probe jobs' own calls pass the gate. A probe that cannot reach the backend fails the check as `ComputeUnavailable`; any other probe failure is that probe's absence. An answer that is no `Capabilities` (`handshake.capabilities_from_answer`) is a `VersionMismatch` when it carries an `app_version` (a worker of another release), naming both contract numbers when it carries a `protocol_version` that differs, and both app versions, else a `ComputeUnavailable` (the URL is no worker). `WorkerBackend.capabilities()` is the one worker read outside the gate (a session request with `gated=False`, signed with the backend's token): the check reads it, and neither passes nor re-arms the gate. A `requests.ConnectionError` through the session (a gated call) or an `OSError` from the legacy websocket connect re-arms the checks of the backends on its URL (`reset_handshake(url)`); one from the `/v1` submit socket the checks of the backends on its URL (`reset_handshake(url)`). TLS trust: `subprocess_operations.trust_ca(worker_url, pem)`, which every `WorkerBackend(url, ..., ca_cert=...)` calls, builds one `ssl.create_default_context(cadata=pem)` per worker URL from a non-empty PEM (a later call replaces it, and one with no PEM drops it and its adapter, so a row removed and added again is trusted as the new row says; nothing on disk), mounts it on `_worker_session` at `f"{worker_url}/"` as an `HTTPAdapter` (`_TrustedCa`, `ssl_context=`), and `ssl_context_for(worker_url)` hands it to both sockets' `connect(..., ssl=...)` (`None`, the public CAs, for every other worker), so the gate, its probe, the task routes, `/v1`, `capabilities()` and both submit sockets verify that worker against it; a worker whose certificate does not verify is unreachable (`requests.exceptions.SSLError`, a `ConnectionError`, or `ssl.SSLCertVerificationError`, an `OSError`). So a worker call of any kind can raise `VersionMismatch` or `ComputeUnavailable` (neither is a `RequestException`), and every caller that degrades on `RequestException` handles `ComputeError` too: `clear_task_from_worker`/`cancel_task` log and return `False`, a status poll that loses the worker fails the task as `ComputeUnavailable` naming the backend, `trigger_apply_table_edits`/`trigger_add_key_column` and the virtual-table materialize raise `WorkerUnavailableError`, the catalog metadata, preview and history reads let it through and turn a connection error into `ComputeUnavailable`, never a read in core, `/system/worker_pool` answers 503 `WORKER_UNAVAILABLE`, and the custom-node dry run answers an unreachable worker as a `load` error, at submit or while it follows its task through `WorkerBackend.status` (`ComputeUnavailable`), and lets any other `ComputeError` reach its route, which answers 500 with the message. The dry run's status, result, cancel and clear go through the worker backend (`status`, `task_result`, `cancel`) and `clear_task_from_worker`, the helper `release` uses, since no protocol call clears a task by id.
- **Reads that are not a node's result.** With `FLOWFILE_COMPUTE_PROTOCOL` on: the REST "Fetch sample" route runs `run_op(rest_api_read)` on the worker backend with the node's pagination capped at one page of `sample_size` records, samples that result and releases it; the published-flow runner reads a non-local run's response as `sample(ref, n)` on the api_response node's reference through the backend that holds it, `n` being `max_rows` clamped to 10 000, the worker's sample cap (an unset `max_rows` too), the response saying `truncated: true` when the cap left rows out (`api_runner._truncated`, the result's row count from its reference, else a `count`), while a local run still collects in core, and closes the flow once the response is serialised or on any error, so the call holds nothing after it answers; a virtual table's preview samples the reference its producer run holds (`VirtualTableService.held_virtual_flow_table`, which keeps it until the read is done) on that reference's backend and counts it for `total_rows`, and a table that resolves without a run (a query table, an optimized one whose sources are current) reads its plan through `head_rows` and `count_rows` on the current context's backend. None of them opens a file a backend stored, and the worker's virtual-table snapshot is read only with the flag off. In both flag states, a kernel custom node's dry run reads the outputs its kernel wrote through `bounded.head_rows` and `count_rows` on the current context's backend, the one that wrote its inputs, and the AI agent's post-apply observation and its code-node dry run take a node's rows by `sample(ref, n)` on the backend that holds its reference, never by collecting its engine.

## Gotchas
- **A worker failure never continues in core.** A plan the worker cannot load, a killed or timed-out child, an unreachable worker or one on other versions ends the node with a typed `ComputeError` (`PlanRejected`, `TaskFailed`, `ComputeUnavailable`, `VersionMismatch`; `flowfile/execution/errors.py`), downstream nodes are skipped, and the published data API answers 503 or 500. A read of a node whose last run failed (`get_resulting_data`, `get_output`) raises that run's exception, which the executor keeps, never the plan the run built before the failure; a node skipped below it drops what it held, so its read raises its input's error, and a node that completed keeps its result. Do not add a path that collects in core when the worker fails; the worker is the only compute, embedded in this process for a `"local"` flow or a default set to `local`, beside core otherwise. An unreachable worker is never a cache miss: `results_exists` raises instead of answering `False`.
- **The first use of each backend in a process is a handshake** (`flow_data_engine/subprocess_operations/handshake.py`): any call through the worker session or the WebSocket submit can raise `VersionMismatch` or `ComputeUnavailable`, neither of which is a `requests.RequestException`. A caller that degrades on connection errors must handle `ComputeError` too. No module but `configs/settings.py` and `flowfile/execution/registry.py` may read `WORKER_URL` or `OFFLOAD_TO_WORKER`, and the four execution directories must not gain an inline `execution_location` compare: `tests/flowfile/execution/test_inline_location_branches.py` asserts both counts are zero. Ask the registry (`default_backend_id`, `worker_url`, `child_env`) or the backend you hold, and read a run's parallelism from `current_context()`.
- **Never bind a patched collaborator in a `flow_graph` submodule.** Tests patch names like `get_kernel_manager` or `ExternalRestApiFetcher` on the package root, and several only assert a call did *not* happen, so a submodule importing its own copy passes while checking nothing. Read them as `root().<name>` and add new ones to the bind-surface block of `__all__`.
- `flowfile_core/__init__.py` runs `validate_setup()` then `init_db()` **on import** — importing the package has side effects (DB file creation, Alembic schema migration, default-user seeding).
- Don't route full-dataset compute around the execution context's backend (no collect in core outside the sanctioned bounded reads), and don't add eager litellm imports anywhere under `ai/` — both break invariants enforced by tests. `tests/flowfile/execution/test_serving_app_ratchet.py` walks `flowfile_core/` and `flowfile/web/` for a `.collect(` over a `plan_for` result (the call, a chain over it, or a name bound to one) and asserts there is none: only a process that does not serve, the holder, collects a leaf that way.
- There is no package-level `pyproject.toml`; deps, scripts, ruff, and pytest config all live in the monorepo-root `pyproject.toml`. The local `.env` is read by `settings.py` via Starlette `Config`.
- Kernel / AI-local-model / Docker features need Docker available; absence surfaces as runtime errors, not import errors.
- **`FLOWFILE_SECURE_STORAGE_PATH` relocates the electron `SecureStorage` dir** (`jwt_secret` / `master_key` / `internal_token`). Set by `tests/conftest.py` and `flowfile_frame/tests/conftest.py` before any core import (`_storage = SecureStorage()` runs at `auth/secrets.py` import) so suites don't write into the developer's real `~/.config/flowfile`. **`flowfile_worker` honors the same var** (`flowfile_worker/secrets.py`) — it must, because core encrypts `$ffsec$` secrets with the master key in that dir and the worker re-derives it independently; a split store makes every worker-offloaded secret decrypt fail ("Task failed"). So a worker started by hand in another shell needs the var exported too, or core's suite (which reuses a running worker on an explicit `FLOWFILE_WORKER_PORT` or with `FLOWFILE_TEST_REUSE_WORKER=1`) will diverge from it. The electron `internal_token` is persisted there so CLI subprocess runs (manual + scheduled) present the same kernel→core token as the server.
- **The test session never silently reuses a worker on the default port.** With `FLOWFILE_WORKER_PORT` unset and something already answering on 63579 (a dev worker, or the desktop app's packaged sidecar), `tests/conftest.py::_claim_worker_port` moves the session to a free port at import and `managed_worker` starts a worker built from this checkout there (`poetry run flowfile_worker --port …`); the report header names the port. `FLOWFILE_TEST_REUSE_WORKER=1` opts back into reusing the running one. An explicit `FLOWFILE_WORKER_PORT` is used as given and a worker already listening there is reused, so a pinned port pointing at a stale worker still runs against it (`test_telemetry_events.py::TestWorkerOffloadedFailuresKeepTheirClass` then fails). The suite's worker still posts its logs to `CORE_PORT` (default 63578), so set a private `CORE_PORT` too when a live core is running.
- **The formula node holds an ordered LIST of entries.** `NodeFormula.functions` is authoritative; `function` is the legacy single-entry field. The after-validator fills `functions` from `function` and mirrors it back — the SAME object — only when there is exactly one entry, and the serializer drops the `function` key entirely for zero or 2+ entries so an older Flowfile fails visibly instead of silently running only entry 1. Entries are evaluated **sequentially** (`flow_data_engine/formula_entries.py::apply_formula_entries`, one `with_columns` + `collect_schema` per entry (resolved over an empty frame of the input's schema when the caller passes one, as `apply_sql_formulas` does with the protocol flag on); `FlowDataEngine.apply_sql_formulas` is the run-time wrapper and `formula_entry(position, FunctionInput)` the one place a declared type resolves to a cast target): entry N sees the base columns plus the outputs of entries 1..N-1, the deliberate opposite of `multi_field_formula`, which puts every expression in ONE `with_columns` so each reads the ORIGINAL values. Failures are attributed to a row by `FormulaEntryError(position, output_name, detail, kind)`. **One classifier words every failure**, on every surface: `build_expression` (parse) and `classify_polars_error` (missing_column / type) in `formula_entries.py` are what the run-time engine, the chain check *and* the preview's active-row evaluation (`extensions.py::evaluate_preview_entry`) all raise through, so the row strip and the preview banner can never disagree (pinned by `test_real_time_interface.py`'s parity cases); `classify_polars_error`'s optional `schema` argument is what lets a type error name the text column and the cast that fixes it — `text_dtype_hint`, shared with the single-expression `check_expression`. `parse_detail` curates the parser's non-`ExpressionSyntaxError` failures — an unclosed `[` is a bare `IndexError` ("string index out of range") from the tokenizer and becomes `column reference is not closed, add ]`; anything else non-parser becomes `expression could not be parsed` — raw `str(e)` of an internal exception never reaches the user. A `missing_column` close to an existing column (difflib, cutoff 0.6, judged against the schema the entry actually saw) carries a `ColumnSuggestion` and the hint is folded into `detail` itself (`column 'regiOn' not found, did you mean 'region'?`).
- **Edit-time formula checks walk the same chain.** `_extensions/real_time_interface.check_expression_chain(schema, [FunctionInput(...)])` resolves each entry by running `apply_formula_entries` itself against an empty LazyFrame (data-free) and translating `FormulaEntryError` into a positional `ExpressionIssue`, so the editor and the engine cannot drift and returns one positional issue slot + one accumulated schema per entry. Each step also **collects** that zero-row frame, because `collect_schema` alone accepts the `.dt`/`.str`/`.list` namespaces unexamined (`format_date` on a text column resolves clean and only fails on collect); that failure goes through the same `classify_polars_error`, so the extra depth costs no wording drift. **Cascade suppression is load-bearing**: a failing entry still contributes its declared output column (String under Auto), so one broken row does not light up every row below it. Blank expression ⇒ no issue and no column; blank output name ⇒ `config`; a duplicate output name warns (`duplicate`) on the later entry without blocking the run; an unclassifiable failure yields no issue at all. `settings_validation._formula_chain_issues` consumes it and drops `missing_column` issues (the column phase reports those, having subtracted earlier entries' outputs); it labels a single-entry node `Invalid formula:` and a multi-entry one `Formula N ("name"):`, matching `str(FormulaEntryError(...))` — both prefixes come from `formula_entries.entry_label`. `settings_validation.node_formula_chain_issue` is the chain counterpart of `node_expression_issue`: the first `type`/`parse` entry, which is what `add_formula` returns as `(False, message)` and what the executor's `_raise_on_invalid_expression` gate raises on, so a formula node fails at itself rather than at a downstream sink.
- **Two POST routes back the multi-formula drawer** (same router auth as `instant_result`, no trailing slash): `/custom_functions/formula_chain_check` returns `{available, base_columns, entries:[{issue, columns}]}` for the editor's *unsaved* entries (`available=false` when the input schema cannot be resolved — silence over guessing), and `/custom_functions/formula_chain_instant_result` evaluates entry `index` on the one preview row with the entries above it applied first. Logic lives in `flowfile/extensions.py`; the routes stay thin. A chain issue is `{message, kind, suggestion}` where `suggestion` is `{kind: "replace_column", from, to}` or null (`FormulaChainSuggestion`; `from` is a keyword, hence the `from_column` field + alias) — additive, so an older frontend ignores it.
- **Exported code must bind what the node had.** A Polars-code node runs in `PolarsCodeParser.safe_globals`, which provides `col`, `lit`, `cs`, `expr`, every dtype by bare name, `BytesIO`, `ZoneInfo`, `base64`, `datetime`, `time`, `decimal` and `zoneinfo` besides `pl` — `pl`, `cs`, `expr` and the stdlib names as narrow namespaces, never the modules, since a module's submodules reach `os` (`pl.config.os`, `datetime.sys`); the Polars export inlines the code, so `code_generator._sandbox_imports` adds the import for each of those names the code reads — a namespace by the real module it stands for (`_SANDBOX_NAMESPACE_IMPORTS`), the rest **derived from the sandbox dict itself** (`_sandbox_import_table`: a module by its name, a Polars export from `polars`, anything else from the public module defining it), so a sandbox addition that is no namespace needs no table edit (`test_every_sandbox_name_gets_an_import_binding_the_same_object` pins each statement binds the sandbox's object; the FlowFrame export passes the code to `polars_code`, which runs it in the sandbox). Stored values — manual-input rows, a flow input's sample, the frame's own argument reprs — go through one renderer, `code_generator/literals.py::python_literal`: a NaN or infinity is written `float("nan")`, a date, time or zone gets its module import, and a decimal is `decimal.Decimal('…')` (never `Decimal(...)`, which the sandbox import `from polars import Decimal` would shadow). `native_handlers.value_literal` is the other thing: a pure-literal check (round-trips through `ast.literal_eval`, no imports) for settings values that must stay plain data.
- **Code export always chains a formula node's entries** — one `with_columns` call per active entry, in order, in both dialects (`code_generator/transform_handlers.py::_handle_formula` and the `FlowGraphToFlowFrameConverter` override); never a fused call for independent entries, never the `flowfile_formulas=[...]` list form for a whole node. A later entry may read a column an earlier one writes, and a chain shows that where a keyword form whose evaluation is silently sequential does not. Per entry the native expression is preferred and only that entry falls back (`simple_function_to_expr` / the single-entry `flowfile_formulas=` form). One-entry output is pinned by `tests/flowfile/test_formula_multi_entry.py::test_one_entry_emission_is_unchanged`: byte-identical to the pre-multi-entry baseline except the FlowFrame native row, which now pins an untyped entry (a typed one keeps the keyword form). This is the deliberate asymmetry with `flowfile_frame.with_columns`, which collapses independent expressions into ONE node (`formula_dependencies.entries_are_independent`, still used there only): a multi-entry node exports as a chain and re-imports as N single-entry nodes.
- **A formula node only travels in a share link with exactly one entry** (`share/compatibility.py::_formula_reason`) — WASM's `nodes_formula.py` reads `settings["function"]` alone and passes the frame through when it is absent, so a multi-entry node would run green-and-wrong in the browser.
- **Community-node installs are admin-gated** (`require_admin`, same reasoning as custom-node mounts — they land executable code install-wide) and tracked by a `community_receipts.json` sidecar living **inside** `user_defined_nodes/` next to the flat `<id>.py` files (never touch non-community files on uninstall). Consent + the client's sha256 pins are advisory; `installer.py` re-scans downloaded bytes and is authoritative — it also refuses blocklisted ids (410), yanked versions (410 `YANKED`), and `min_flowfile_version` mismatches (409 `INCOMPATIBLE_VERSION`); install never execs the node module (lazy exec at placement via `registry.ensure_class`). For offline/local UI work set `FLOWFILE_COMMUNITY_INDEX_URL` to a local `index.json` path (**fixture mode** — no GitHub repo needed).
- **In-app PR publishing must never surface a GitHub-domain failure as HTTP 401** — the frontend axios interceptor treats 401 as JWT expiry and would trigger a refresh/logout. `community_github.py` / `publish-pr` map GitHub errors to typed `error_code` payloads on non-401 codes instead (412 `GITHUB_NOT_CONNECTED`/`GITHUB_TOKEN_INVALID`, 410 `DEVICE_EXPIRED`/`DEVICE_DENIED`, 502 `GITHUB_API_ERROR`/`GITHUB_RATE_LIMITED`, 503 `GITHUB_NOT_CONFIGURED`, 409 `VERSION_NOT_INCREMENTED`). The device-flow client id comes from `settings.get_community_github_client_id` (env var → `.env` → baked `COMMUNITY_GITHUB_CLIENT_ID_DEFAULT`, so non-empty by default; an empty resolution ⇒ device flow disabled, PAT + bundle still work).
- **`enable_cdf=True` means "ensure enabled", not "on create".** `shared/delta_utils.write_delta` / `merge_into_delta` create a new table with the CDF property, and on an existing untracked table call `enable_change_data_feed` (a `SET TBLPROPERTIES` commit) *before* writing so the write lands above the floor — the catalog already enables first, so it is a no-op there. A cloud Delta path has no `CatalogTable.cdc_enabled_version`: its floor comes from `get_change_data_feed_floor`, which walks `DeltaTable.history()` for the newest `SET TBLPROPERTIES` that turned CDF on (a JSON-string `properties` parameter is decoded) and otherwise falls back to the oldest retained version, not a hardcoded `0`, because log cleanup can drop early commits.
- **Cloud nodes resolve their connection only through `flow_graph/cloud.py::_resolve_cloud_node_connection(settings, user_id, role)`** — path guard first (`validate_cloud_resource_path`; docker also refuses absolute local paths), then the own-first/group-granted connection or the ambient fallback (refused in docker). In docker a server-identity connection (`sharing.SERVER_IDENTITY_AUTH_METHODS`: `aws-cli`, `env_vars`, `iam_role`, `managed_identity`) is admin-only: `routes/cloud_connections.py` 422s a non-admin create/update and `db_connections.get_cloud_connection_schema` raises `CloudConnectionNotAllowedError` when the row's owner is not an admin (admin-owned rows, shared ones included, keep working). Never call the guard and `get_cloud_connection_settings` separately, and never put a strict validator on `CloudStorageSettings.resource_path`: `manage/io_flowfile.py` re-parses saved node settings with a bare `model_validate`, so an unconfigured cloud node would stop its whole flow from opening. The empty-path node description reads `Write (no path set) (…)` / `Read (no path set) (…)`.
- **Saved `aws-cli` connections read credentials from `cloud_storage_connections.aws_profile`** (blank/NULL ⇒ boto3's default chain), never from the connection's display name. Migration 033 adds the column **without a backfill** (maintainer decision — don't re-add a name-as-profile backfill); `db_connections._aws_profile_to_store` keeps the profile for `aws-cli` only, and `update_cloud_connection` keeps the stored profile when the caller omits `aws_profile`. Project export/import round-trips `aws_profile` (NULL for files written before it existed) and the session token as a `${secret:…}` placeholder. `aws_session_token` (access_key) is stored encrypted in `aws_session_token_id` and lives and dies with its key pair: a blank value on update keeps it only while the key ID and secret are unchanged; a new key ID or secret without a token, or another auth method, deletes it. It is deliberately **not** counted as a new credential by the sharing re-point guard.
- **With `FLOWFILE_COMPUTE_PROTOCOL` on, a cloud read's plan names its saved connection instead of carrying its credentials.** `CloudStorageReader.get_read_credentials` gives a Polars scan of a stored connection whose method holds a credential (S3 access key, IAM role, `aws-cli`; Azure key, SAS, service principal; GCS service account) the transport options only (`get_plan_storage_options`) and a `CredentialRefProvider(connection id, user id)` (`credential_ref` looks the id up by the same own-then-granted rule), so core resolves nothing to build it; whichever process runs the plan resolves it: a worker with its own catalog database, master key and AWS identity (a behaviour change for `aws-cli` and `iam_role`), core when core runs it, including the schema a reader takes at construction, except a catalog table read of an object-storage namespace (`builders/catalog.py::_add_catalog_table_reader`) and a cloud storage reader's plain read (parquet, CSV, NDJSON or Delta, a file or a directory: `builders/cloud_storage.py::add_cloud_storage_reader` → `FlowDataEngine.from_cloud_storage_obj(..., backend=...)`), which with the flag on take their schema at construction from the backend the reader runs on (the one placement assigns the node in a run, the graph's outside a run): the plan or scan is held there deferred with no preview for the block of `bounded._deferred`, which a worker beside core answers in a pooled child (so the connection resolves on the worker) and the embedded worker in this process, and a directory's first-file schema is read in core only without a backend; the SQL, change and virtual reads of such a namespace and the cloud change read still resolve their schema in core. `env_vars` and managed identity carry no provider; with the flag on an `aws-cli` S3 plan with no region of its own carries its profile's region (`cloud_storage_reader._profile_region`), never a credential, and a cloud reader's scan of an `aws-cli` read with no saved connection carries no credential and no provider either, Polars' default provider resolving the default chain where the plan runs, while a cloud change read of one still carries core's; a GCS connection with an endpoint is read the same way, its endpoint reached through object_store's `gcs_base_url` in a service-account key with no key material and OAuth off (`get_plan_storage_options`), so its plan carries the provider and no key (`env_vars`: no token at all), and with the flag off it is read through gcsfs in core with the key in its options (`token` is not among `PROVIDER_CREDENTIAL_KEYS`); the flag off keeps the `$ffsec$` provider for the rest; with the flag on a read naming a connection the catalog does not hold for its user, or given no user, is refused (`ValueError` naming the connection), never resolved in core, an in-code connection being stored first (`flowfile_frame`'s `create_cloud_storage_connection` stores it for the frame's user), while a read with no saved connection keeps core's (the cloud change read's `aws-cli` one). A remote worker therefore needs core's catalog: the same SQLite file co-located, the shared Postgres catalog on another host. The other plans that read a stored connection name it the same way: a cloud change read through `flow_graph/cloud.py::_cloud_change_scan_kwargs`, and every catalog scan of an object-storage namespace (table, SQL and change reads, a query virtual table's cloud sources, the SCD2 writer's output) through `CatalogStorageTarget.scan_kwargs`: with the flag on the target holds the namespace connection's `credential_ref` for the catalog owner and its `plan_storage_options`, and each call makes a new provider, so a target the reader resolved at wiring still resolves once per plan. Core's own reads of those tables keep the resolved `storage_options`, and the writes `worker_interface`.

- `flowfile_core/project/` — git project-tracking: `projection.py` (DB→files, never-raise hooks), `importer.py` (files→DB), `service.py` (lifecycle), `git_ops.py`.
