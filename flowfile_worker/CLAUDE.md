# CLAUDE.md - flowfile_worker

Standalone FastAPI compute service that offloads heavy Polars/data work from `flowfile_core`, running each job in a spawned subprocess. Package-specific notes; see the root `/CLAUDE.md` for monorepo-wide setup, build, lint, ports, and cross-package contracts.

## Role
- Separate FastAPI service on **port 63579** (`configs.DEFAULT_SERVICE_PORT`). Core (port 63578) is its only client. A worker on another host needs what `docs/users/deployment/remote-worker.md` (repo root) lists; the protocol it serves is `docs/for-developers/compute-protocol.md`. With `FLOWFILE_COMPUTE_PROTOCOL` on, core's default, its `WorkerBackend` speaks the versioned `/v1` wire (`protocol_routes.py`, `/v1/ws/submit`); core still calls the task routes for the write kinds, the Delta operations, the visualisation session, the catalog services, the custom-node dry run and the handshake (`GET /capabilities` and its plugin probe), and for everything with the flag off: core's `subprocess_operations.py` POSTs serialized Polars LazyFrames to `WORKER_URL/submit_query/` and polls `/status/{id}`, or streams over `/ws/submit`.
- The worker calls **back to core** at `FLOWFILE_CORE_URI` (`configs.get_core_url(CORE_HOST, CORE_PORT)`, default `http://<CORE_HOST>:63578`) only for log shipping: `flow_logger.FlowfileLogHandler` POSTs to `/raw_logs`, signed with core's `X-Internal-Token` header (core refuses unsigned posts).
- Core ships paths/JSON and never materialises LazyFrames; the worker holds dataset memory. Results land as Arrow IPC files under `CACHE_DIR/<flow_id>/<task_id>.arrow`; the serialized `scan_ipc` plan (not the data) is returned to core via the WS binary frame / REST `status.results`.
- Runtime contract: every heavy job runs in a `spawn`-context child process, unless the host set `spawner.in_process`, the embedded worker's in-process mode for a library host, which gives up cancel, the task time limit and OOM isolation by design. The FastAPI process only spawns, monitors shared `Value`/`Array`/`Queue`, ships paths, and kills children. It must stay lean — no large dataset in the parent.

## Layout
- `flowfile_worker/main.py` — FastAPI app (`shutdown_handler` lifespan; includes `routes.router`, `streaming_router`, `protocol_routes.router` and `streaming.v1_streaming_router`) + `run()` entrypoint; lifespan calls `viz_session_registry.shutdown()`, terminates `mp_context.active_children()`, runs `storage.cleanup_directories()`; `/shutdown` endpoint + SIGTERM/SIGINT handlers + `start_parent_death_watcher`. Its `RequestValidationError` handler answers FastAPI's own 422 shape without each error's `input`, which repeats the body (an export or import body's presigned URI); in single-file mode core's app, which mounts these routers, answers with its own copy.
- `flowfile_worker/__init__.py` — process-global state: `mp_context`, a spawn context whose `Process` (`SpawnProcess`) forces the `spawn` start method and stamps a `__main__` that has no spec with `flowfile_worker.__main__`'s as the first child starts, never at import, so `import flowfile_worker` leaves the importing process's start method and `__main__` alone; `status_dict`, `process_dict`, locks, `CACHE_DIR`, `PROCESS_MEMORY_USAGE`. `Status`/`models`/`configs`/`external_sources`/`secrets` are exposed **lazily** (PEP 562 `__getattr__`) behind an explicit `__all__`, so a bare `import flowfile_worker` does not pull `models`/pydantic.
- `flowfile_worker/routes.py` — REST endpoints (`/submit_query/`, store_sample/write/create_table, catalog materialize/sql_query/delta/visualize, train/apply ML, add_fuzzy_join, execute_custom_node, status/cancel_task/clear_task, `GET`/`POST /pool` warm-pool state/resize). `GET /capabilities` answers with `protocol_routes.worker_capabilities()`, as `GET /v1/capabilities` does: `shared/compute_protocol.py::local_capabilities()` (app, Polars, Python and protocol versions, `platform` (`sys.platform-machine`), the installed plugin versions and, per Polars expression plugin, the library path relative to `sys.prefix` exactly as a plan serialises it — the fields that have to match between the process that serialises a plan and the one that runs it) with what the worker declares (Key patterns). A request to any route on this router that carries a foreign `X-Protocol-Version` is answered as usual and logged as a warning (`warn_on_foreign_protocol_version`, a router dependency like the token check). The ten task routes whose work the `/v1` routes do and which core no longer calls with the protocol flag on (`/store_sample/`, the four `/store_*_read_result` reads, `GET /kafka_offsets/{task_id}`, `/create_table/{file_type}`, `/train_ml_model`, `/apply_ml_model`, `/add_fuzzy_join`) answer `Deprecation: true` (`deprecated_route`, a dependency on each; an error answer carries no header); `test_deprecated_routes.py` pins the set.
- `flowfile_worker/streaming.py` — `streaming_router` WebSocket `/ws/submit` (binary in/out, progress frames, disconnect hand-off to `handle_task`), and `v1_streaming_router` WebSocket `/v1/ws/submit` (the `/v1` submit over one connection: `protocol_routes.run_submit` in Starlette's threadpool, progress frames from its `status_dict` entry; contract under Key patterns).
- `flowfile_worker/service.py` — the bodies of the `/v1` routes as plain functions over the wire models, one per route (`worker_capabilities`, `run_submit`, `sample`, `count`, `exists`, `release`, `export`, `import_uri`, `job_status`, `cancel_job` and the twelve operations), each raising the `HTTPException` its route answers (404 not held, 422 refused before anything runs, a child's 500 through `_failure`); the request and answer models (`SubmitMeta`, `OpOutputs`, `RandomSplitInput`, `MlTrainInput`, `MlApplyInput`, `PolarsCodeInput`, `SqlQueryInput`, `CredentialRefBody`, `ExportBody`, `ImportBody`), `OPERATIONS`, the sample caps, the materialisation policy and `sweep_expired` live here. Called by the routes and, in the same process, by core's embedded worker adapter (`flowfile_core/flowfile/execution/backends/embedded.py`), which passes the models and maps the exceptions; no router, `Query`, `File`, `Form` or `Response` here, and `sample` checks its cap itself.
- `flowfile_worker/protocol_routes.py` — the versioned `/v1` router: `GET /v1/capabilities` (`worker_capabilities()` over `OPERATIONS`, which the legacy route answers too), `POST /v1/submit`, `GET /v1/results/{id}/sample?n=`, `GET /v1/results/{id}/count`, `HEAD` and `DELETE /v1/results/{id}`, `POST /v1/results/{id}/export` and `POST /v1/results/{id}/import` (bodies `ExportBody` and `ImportBody`, a credential as `CredentialRefBody`), `GET /v1/jobs/{id}`, `POST /v1/jobs/{id}/cancel`, and the operations `POST /v1/ops/<kind>` with their answer `OpOutputs` and the bodies of their own, the random split's `RandomSplitInput` and the ML kinds' `MlTrainInput` and `MlApplyInput`; each route delegates to its function in `service.py` and answers what it returns. The `require_protocol_version` dependency (it takes an `HTTPConnection`, so `/v1/ws/submit` calls it too), `parse_submit_meta`, `JobId` and `ARROW_STREAM` are the router's own; the models, `run_submit`, `worker_capabilities`, `sweep_expired`, `OPERATIONS` and the sample caps are re-exported from `service.py`, so importers take them from here as before. Contract under Key patterns.
- `flowfile_worker/results.py` — `ResultRecord` and the `results` registry (`ResultRegistry`, a dict under a lock) that holds what `/v1/submit` produced and when each submit under an id ended (`mark_ended`, a monotonic stamp taken for failed submits too; `pop` forgets it; `expire(max_age)` drops every id stamped that long ago with its record and file and returns the ids), plus `result_path(flow_id, result_id)` (`CACHE_DIR/<flow_id>/<result_id>.arrow`, the legacy layout, so the lifespan's cache cleanup covers it). A `ResultRecord` of `kind="blob"` is a path and nothing else: a materialised record with no columns and no row count whose file holds a blob's bytes, answered as `WorkerLocation(kind="blob", path)` and a wire `ResultRef(kind="blob")`; `pop`, `expire` and `_held` treat it as any materialised record, its file going with it. Parent-only: nothing a spawned child imports reaches it. For `/v1` it is the result half of `status_dict`: no scan plan or result path goes into a `Status`.
- `flowfile_worker/spawner.py` — `start_*` helpers (`start_process`, `start_generic_process`, `start_fuzzy_process`, `start_train_model_process`, `start_apply_model_process`, `start_custom_node_process`) that build shared mem + spawn `mp_context.Process`, plus `handle_task` monitor loop and the `process_manager` singleton. `in_process` (default `False`) is the host's choice: set, each `start_*` hands its target and kwargs to `run_inline` before any pool lease or primitive, which calls the target in the calling process with the three primitives (a `pool._ResultSlot` as its queue), records an `Exception` that escapes it through `record_task_failure`, and writes the job's end into `status_dict` as `handle_task` writes a child's (`Completed` with `results` and `number_of_records`, `Error` with `error_kind` and `error_message`, `Unknown Error`; an entry marked `Cancelled` is left so); no `process_manager` entry, no poll, no time limit, no cancel. `FLOWFILE_WORKER_POOL_SIZE=0` is spawn-per-task, never in process. Core's embedded worker adapter (`flowfile_core/flowfile/execution/backends/embedded.py`) also calls `service._run`, which starts through `start_process`, with the task routes' operations and keyword arguments (`write_output`, `write_to_database`, `write_to_cloud_storage`, `write_delta`, `merge_delta`, `scd2_delta`), and `viz_sessions.viz_session_registry.execute` directly, until 4.10 moves those kinds to `/v1/ops` bodies.
- `flowfile_worker/pool.py` — warm process pool (boot size: `FLOWFILE_WORKER_POOL_SIZE` env override > UI-saved `<internal storage>/worker_pool.yaml` (`initial_pool_size()`, written on every `POST /pool`) > the default — **on with 4 members on every platform** via `default_pool_size()`): `TaskPool`/`PoolMember` parent-side lifecycle + `member_loop` child entrypoint. Members inherit their `Value`/`Array`/queues at spawn (Windows: sharedctypes can't travel through queues) and always put one `(_TASK_DONE, payload)` envelope per task, so the drain never guesses which ops produce results. Runtime-resizable via `GET/POST /pool` (routes.py; core admin-gates access through `/system/worker_pool`, surfaced as a live dashboard on the frontend's Compute page → admin-only Performance tab: warm/busy tiles, `active_tasks` from status_dict, lifetime `tasks_completed`, per-member pid/state/tasks/RSS table) — growth prewarms immediately, shrink retires idle members now and busy ones at next checkin. Like every `routes.py` endpoint, `/pool` requires the `X-Flowfile-Internal` token (see Key patterns); core additionally admin-gates it through `/system/worker_pool`. Members are spawned `daemon=True`: mp's atexit terminates daemons but *joins* non-daemons, and an idle member blocks in `task_q.get()` forever — a non-daemon member would hang any process (pytest, embedding) that exits without running the lifespan shutdown. Import-lean by contract — every pool child imports it (`test_pool.py::TestModuleHygiene`).
- `flowfile_worker/process_manager.py` — `ProcessManager`: lock-guarded `task_id -> Process` map with `cancel_process` (terminate + join).
- `flowfile_worker/funcs.py` — the actual subprocess targets (store, store_sample, submit_result, split_result, export_result, fuzzy_join_task, write_*, merge_delta, train/apply model, resolve_virtual_table, execute_sql_query, sql_query, catalog metadata, `generic_task`). Imports polars at module top; everything heavier (`models`, `pl_fuzzy_frame_match`, the external-source connectors, `shared.delta_utils`, `catalog_reader`, `shared.excel_writer`) is imported **at use** inside the task that needs it, because every spawn pays this module's top-level imports.
- `flowfile_worker/custom_node_runner.py` — spawned-child target for custom nodes: installs SDK import aliases, loads the node from shipped source text, decrypts `$ffsec$` secrets locally (`WorkerSecretResolver`), runs `process(*LazyFrames)`, writes per-output Arrow IPC (dry runs return preview/logs/duration in the queue payload).
- `flowfile_worker/task_errors.py` — the single seam that records why a task failed: `describe_exception` (class-prefixed description core can parse) + `record_task_failure` / `record_task_failure_text`. Stdlib-only; every spawned child and pool member imports it.
- `flowfile_worker/models.py` — Pydantic request/response + `Status`, `OperationType` literal, `Base64Bytes` JSON-safe bytes type; re-exports `RawLogInput` from `log_models`.
- `flowfile_worker/log_models.py` — `RawLogInput` as a plain dataclass. Deliberately pydantic-free: `flow_logger` is on every spawned child's import path, so taking it from `models` would drag pydantic + the external-source models into every task.
- `flowfile_worker/configs.py` — host/port arg parsing, `FLOWFILE_CORE_URI`, `TEST_MODE`, logger.
- `flowfile_worker/secrets.py` — independent Fernet/HKDF secret derivation (mirrors core).
- `flowfile_worker/utils.py` — `collect_lazy_frame*` helpers; importing it registers the worker's decryptor for cloud credentials embedded in core-built plans (`shared.cloud_credential_provider.register_secret_decryptor`). `funcs.py` and `custom_node_runner.py` import it at module top, so every plan-running child has it.
- `flowfile_worker/catalog_reader.py` — the only two catalog-open primitives (`open_catalog_table`, `open_virtual_result`); polars-at-top, children-only.
- `flowfile_worker/viz_sessions.py` / `viz_session_worker.py` — `VizSessionRegistry` + spawned-child entrypoint for long-lived Graphic Walker (`polars_gw`) viz LazyFrames.
- `flowfile_worker/external_sources/` — `sql_source/`, `s3_source/`, `kafka_source/`, `rest_api_source/`, `google_analytics_source/` connectors run inside subprocesses.
- `flowfile_worker/create/` — `table_creator_factory_method(FileType)` + `create_from_path_*` builders for `csv`/`parquet`/`json`/`excel`; the excel builder is a thin wrapper over `shared.excel_reader.read_excel_table` (the local `read_excel_tables.py` fork of core's reader is gone), and `create/utils.py` re-exports the dtype helpers from `shared.dtype_utils`.

## Key patterns & conventions
- **The service boundary is authenticated and loopback-bound.** Every `routes.py` and `/v1` endpoint and both WebSockets (`/ws/submit`, `/v1/ws/submit`) require the shared internal token in an `X-Flowfile-Internal` header (`auth.py`, enforced once as an `APIRouter(dependencies=...)` — never per endpoint, and never as app middleware, because single-file mode mounts these routers into core's app: `flowfile/web/__init__.py::include_worker_routes` mounts `routes.router`, the `/v1` router and `/v1/ws/submit` under `/worker`, not the legacy `/ws/submit`; a WebSocket route checks `websocket_authorized` itself and closes 1008 before accepting, because FastAPI fills no `Request` for a WebSocket). The token is `FLOWFILE_INTERNAL_TOKEN`, else the `internal_token` entry core persists to the shared secure store, resolved lazily per request so a worker started before core minted it needs no restart; no token found means every request is rejected. `internal_token.py` is the one resolver, shared by `auth.py` (verifying) and `flow_logger.py` (signing log posts), and stays stdlib-only at import because every spawned child loads it; the store fallback imports `secrets` (pydantic) only when the env var is absent. The app-level `/docs`, `/openapi.json` and `POST /shutdown` are deliberately exempt — the Docker HEALTHCHECK, the Tauri readiness probe and the Tauri shutdown ladder depend on it. `/shutdown` is answered only for a loopback transport peer (`request.client.host` parsing as a loopback IP; 403 otherwise, and forwarded headers are not consulted), so the desktop shell on the same host can still post to it while nothing else can. `DEFAULT_SERVICE_HOST` is `127.0.0.1` on every platform; the Docker `CMD` passes `--host 0.0.0.0` because core lives in another container. The worker serves TLS itself when `FLOWFILE_WORKER_TLS_CERT` and `FLOWFILE_WORKER_TLS_KEY` are set; the token is code execution on the worker, so off a trusted network the transport is what protects it.
- **All compute is `spawn`-context**, unless the host set `spawner.in_process` (above), which runs every job the `start_*` helpers start in the calling process. Spawn only via `mp_context.Process(...)`. Children re-import the package fresh, so `configs.py` skips argparse for non-`MainProcess` workers and falls back to env-var defaults — don't rely on parent-set host/port in children.
- **Subprocess signalling protocol** (every `funcs.*` target): shared `Value("i")` progress (`0`→`100` on success, `-1` on error), `Array("c", 1024)` error message, and a `Queue(maxsize=1)` for the result. `handle_task` (sync) and `_monitor_progress` (WS) translate these into the `Status` object.
- **Failure descriptions lead with the exception class name** and are written only through `task_errors.py` — `record_task_failure(error_message, progress, e)` records `describe_exception(e)` (`"ClassName: message"`, no double prefix, never a dotted module path) and then flips progress to `-1`, in that order, because the parent reads the buffer the moment it sees `-1`. The exception object dies with the child, so this string is the *only* class signal core gets: `flow_node/models.py::recover_error_class` splits it on the first colon and keeps an `isidentifier()` head, which is what makes a worker-offloaded node report `ComputeError` instead of a bare `Exception`. `BaseFetcher.get_result` recovers the class from that same prefix, so it is load-bearing for **every** fetcher path (sampler, output writer, ML, custom node, readers/writers), not just the two `_do_execute_remote` sites — changing the format degrades all of them to a bare `RemoteExecutionError`, which telemetry then buckets as `OtherError`. Handlers therefore catch `BaseException` (a pyo3 `PanicException` is not an `Exception`) and re-raise anything that is not an `Exception` right after recording, so the child still dies exactly as before — only no longer silently. `record_task_failure_text` is the no-prefix escape hatch: the two catalog-edit tasks whose `STALE_WRITE:`/`EDIT_INVALID:` sentinels `routes.py::_raise_typed_edit_error` matches by prefix, and the custom-node dry run, which prefixes itself and then appends a traceback.
- **Failure kind: environment vs task.** A failure of the worker's environment rather than the plan's data is raised as `task_errors.WorkerEnvironmentError` (`environment_failures()` wraps the plan deserialize and the IPC result write; `funcs._load_plan` also treats a schema-resolution failure as one only when `_is_load_failure` says the worker couldn't import a UDF's module (`ImportError`) or load a plugin library (`ComputeError: error loading dynamic library…`); every other schema error — missing column, missing or corrupt source file, a plugin rejecting its inputs — stays a task failure, because degrading would mark the node successful). `record_task_failure` prefixes those descriptions with a `\x01` marker that every parent reader strips via `split_failure` (`streaming._read_error_message`, `spawner.handle_task`), publishing it as `Status.error_kind` and the WS error frame's `error_kind` (`"task"` | `"environment"`; the task time limit is `"environment"` too). Core maps `"environment"` to fetcher error code -1 (the node degrades and continues in core) and anything else — including a worker that sends no kind — to 1 (a real node error), on both the WS and REST paths.
- **Result transport:** bytes results are b64-encoded only at the REST boundary (`status.results` in `handle_task`); the WS path (`_send_completion`) sends raw binary via `send_bytes`. IPC files are the canonical hand-off; `Status.file_ref` points at them. `store`/`generic_task` queue a `(payload_bytes, row_count)` tuple (element 0 byte-identical to the bare payload); `spawner.unpack_result` splits it, surfacing the count as `Status.number_of_records` and in the WS `complete` frame so core skips a `calculate_number_of_records` round-trip. Every other op still queues a bare payload (count → None).
- **The `/v1` wire** (`protocol_routes.py` and the bodies in `service.py`, `results.py`, `funcs.submit_result`). The router's dependencies run the token check, then `require_protocol_version`: a missing or foreign `X-Protocol-Version` is 426 with a detail naming both versions (the legacy routes only warn). A router dependency runs before body validation, so a foreign version is 426, never 422. `POST /v1/submit` is multipart: `plan` a **file part** (Starlette caps a part without a filename at 1 MB and spools a file part to disk uncapped; a manual input's plan carries its rows) and `meta` a plain field holding `SubmitMeta` JSON (`hints`, `inputs`, `result_id` matching `^[A-Za-z0-9_-]+$` because it names the file, `flow_id`, `node_id`), with `extra="forbid"` because core builds it by hand and a dropped field would degrade silently; a bad part is 422, a negative `preview_rows` included (`head(-k)` keeps all but the last k rows), an `inputs` id that is not held is 404 before anything spawns. Every request model a worker route validates, the task routes' included (nested models too, `FuzzyMapping` the one third-party exception), refuses an unknown field with 422, and the routes' shapes are pinned by `shared/tests/test_worker_contract.py`. The route is a sync `def` that waits for its child and answers `shared/compute_protocol.py::SubmitResult` (bytes base64 in JSON), or 500 with `detail={status, error_message, error_kind}` (the legacy WebSocket error frame's fields). A deferred submit with no preview runs in a `funcs.submit_result` child too, which loads the plan and resolves its columns (its UDF modules and plugin libraries load there, a CSV's inference reads there) and collects nothing, under the task time limit and `POST /v1/jobs/{id}/cancel`, never in the serving process. `WS /v1/ws/submit` (`streaming.py`) is the same submit over one connection: a bad token closes 1008, then a missing or foreign version is answered 426 with the REST body (`send_denial_response`), both before accepting; core sends the `meta` JSON as a text frame and the plan as a binary frame; the worker runs `run_submit` in Starlette's threadpool (the one the REST route waits in), sends `{"type": "progress", "progress": n}` from the job's `status_dict` entry while it is `Starting` or `Processing`, on each change and every `_HEARTBEAT_INTERVAL` otherwise, then one `{"type": "complete", "result": <SubmitResult JSON>}` or `{"type": "error", "status_code": n, "detail": …}` (the status and detail the REST route answers for the same failure; any other exception is 500 with `describe_exception`) and closes 1000. A client that goes away does not stop the submit: the route stops sending and waits, and the result is held as for a REST client that left. There is no cancel message; cancel is `POST /v1/jobs/{id}/cancel`. Policy: **materialised** when `must_materialise or (wide and preview_rows is not None)`, else **deferred**; `fanout` is not read. Materialised, the child writes IPC to `result_path` and the ref's `location` is `WorkerLocation(kind="file", path)`; deferred, nothing is written, `row_count` is `None` and the location is `WorkerLocation(kind="plan", plan=<the submitted bytes>)`. A deferred result's `count` and `sample` run its plan again (`calculate_number_of_records`, `submit_result` with `preview_rows=n`) as a throwaway uuid task whose `status_dict` entry is popped when it ends; `sample?n=` above `SAMPLE_ROWS_CAP` (10 000) is 422, refused rather than truncated; up to `SAMPLE_ROWS_IN_PARENT` (1 000) rows of a materialised result are read in the parent, more in a throwaway `submit_result` child over a scan of its file, as a deferred result's are. `funcs.submit_result` queues a dict `{columns, row_count, sample}` (a 2-tuple would be split by `unpack_result`), and `columns` is the **plan's** `pl.Schema`, never one read back from the file: Polars reads an unregistered extension dtype (`geoarrow.wkb`) back from IPC as its storage type. The parent spells it with `schema_to_wire`; the child imports nothing new and stays pydantic-free. The job id is the result id: `status_dict[result_id]` is the job (its `results` reset to `None` once the record is built), `GET /v1/jobs/{id}` answers a copy of that `Status` taken under `status_dict_lock`, its `results` always `None` (until its route has read it the entry holds what the child reported, for a submit a `pl.Schema` and sample bytes, which do not serialise), and `POST /v1/jobs/{id}/cancel` does what `/cancel_task` does and also takes a job still `Starting`: the entry is marked `Cancelled` and its child stopped as its monitor starts, the submit or operation then answering its 500 with `status` `Cancelled` and holding nothing. `HEAD /v1/results/{id}` is 200 only while the record is held and, when materialised, its file exists; `DELETE` removes the file, the record, the job entry and `PROCESS_MEMORY_USAGE`, and a submit under a held id releases it first. `submit_result` is not an `OperationType` (a `/v1` client never names one) and is in `pool.POOLABLE_OPERATIONS`, so a warm member runs it. Every submit and operation first runs `sweep_expired()`: under `status_dict_lock` (always taken before the registry's lock, never after) every id whose submit ended `CACHE_EXPIRATION_TIME` (24 h) ago or more loses its record, its file, its job entry and its `PROCESS_MEMORY_USAGE`, failed submits included. The age counts from the end of the submit, not from the last read, and an expired reference answers `HEAD` 404; nothing sweeps between submits and operations (no thread, no timer). `POST /v1/results/{id}/export` (`ExportBody {uri, credential}`) writes a held result to `uri` as parquet in a throwaway `funcs.export_result` child, a streaming `sink_parquet` of the scan of its file or of its held plan, and answers `{"uri": uri}`; a `file:` URI is sunk to the local path `shared.compute_protocol.file_uri_path` reads from it, never handed to Polars as a URI (Polars refuses `file://C:/…`), so the target's folder is the caller's; a result that is not held is 404, a failed sink the submit's 500, and the result stays held either way; the child logs a failed sink as `Error during export to <the URI cut at its first ?>: …`, Polars' repetition of the URI cut the same way, while the 500's `error_message` keeps Polars' text. `POST /v1/results/{id}/import` (`ImportBody {uri, credential, columns, row_count}`) holds a `scan_parquet` of `uri` (of the local path `file_uri_path` reads, for a `file:` URI), built and serialised here and never run, as the deferred record `id` with the columns and row count core sent: nothing is read at import, so the file need not exist yet, `count` answers the given count without a child, `sample` and `export` run the scan in one, and `DELETE` forgets the record and leaves the file (the record has no `path`); like a submit it sweeps first, releases what the id held, and is stamped at once. Both bodies are `extra="forbid"`, and a credential is `CredentialRefBody {connection_id, user_id}` and nothing else, carried as a `shared.cloud_credential_provider.CredentialRefProvider` in the sink or the scan and resolved by the child that runs it, with its catalog and master key, beside the connection's plain options (`credential_ref_kwargs`: region, endpoint, plain HTTP and TLS, no secret), which the export child and the import route read from that catalog, the import route in the serving process, where a catalog that cannot be read is the 500 `{status, error_message, error_kind: "task"}` an export answers for it and nothing is held; without one the sink or scan takes no provider. `export_result` is not an `OperationType` and is poolable; the task routes run it too, as the operation of a `/submit_query/` or `/ws/submit` task with `uri` and `credential` as its kwargs, when core exports a result it minted over them. **A blob** takes the same two routes in the serving process, with no child: `ImportBody.kind` (`"table"` by default) set to `"blob"` refuses a credential, columns or a row count (422) and has `shared.compute_protocol.get_blob` copy a `file://` URI or `GET` a presigned `https://` URL into `result_path(-1, id)` with a `.blob` suffix, held as a blob record and stamped like an import; the export of a blob record has `put_blob` copy its file to a `file://` URI or `PUT` it to a presigned `https://` URL and answers `{"uri": uri}`, a credential being 422, as a presigned URL carries its own authorisation. Another scheme is 422 naming only the scheme, a copy that fails the 500 `{status, error_message, error_kind: "task"}` with a message naming no URL query, and the blob stays held after a failed export while a failed import holds nothing and leaves no file. `DELETE` removes a blob's file. `sample` and `count` do not refuse a blob (core never asks); such a request fails as a read of a file that is no IPC. Core's embedded worker adapter calls the same bodies in its own process, and for the seven kinds the task routes still serve, `service._run` with those routes' operations and keyword arguments and the visualisation session registry, so every kind in `OPERATIONS` runs on the embedded worker too.
- **The `/v1` operations** (`protocol_routes.py` over the bodies in `service.py`, `funcs.split_result`, `funcs.polars_code`, `funcs.sql_query`). Twelve literal routes `POST /v1/ops/<kind>`, one per kind whose result core samples or holds: `database_read`, `kafka_read`, `google_analytics_read`, `rest_api_read`, `file_read`, `fuzzy_join`, `custom_node`, `random_split`, `ml_train`, `ml_apply`, `polars_code` and `sql_query` (any other kind is 404; the writes and visualisation stay on the task routes, and so do the legacy `/train_ml_model` and `/apply_ml_model`). Each is a sync `def` that waits for its child, as the submit does, and answers `OpOutputs {outputs: {name: ResultRef}, metadata}`. The body is the model the kind's task route takes (`DatabaseReadSettings`, `KafkaReadSettings`, `GoogleAnalyticsReadSettings`, `RestApiReadSettings`, `ReceivedTable`, `models.FuzzyJoinInput`, `models.CustomNodeExecuteInput`), whose `task_id` and `cache_dir` are not read; a file read takes its flow and node as the `flowfile_flow_id`/`flowfile_node_id` query parameters and its reader from `received_table.file_type`, and a directory scan is 422 before anything runs. A random split's body is `RandomSplitInput`: the rows as `operation` (base64), already shuffled by core so the worker only slices, and `splits`, `(name, percentage)` in output order, with `extra="forbid"`. A training's is `MlTrainInput` (the rows as `operation`, `model_type`, `target_column`, `feature_columns`, `params`) and an apply's `MlApplyInput` (the rows as `operation`, `model`, the result id of a blob this worker holds, as a submit's `inputs` are ids, and `output_column`), both with `extra="forbid"`, so a body naming a `staging_path` or a `model_path` is 422: the worker holds the model, and no path to it crosses the wire. A Polars Code run's is `PolarsCodeInput` (the node's `code`, its `inputs` as serialised plans (base64) in connection order, `flowfile_flow_id`, `flowfile_node_id`), with `extra="forbid"`; its child is `funcs.polars_code`, pooled, which runs the code once in the `shared.polars_code_parser` sandbox over the input plans and answers a LazyFrame over sources with its resolved `pl.Schema` and serialised plan, nothing collected, or writes a DataFrame, or a LazyFrame that reads a frame held in memory, collected, to its file and answers its `pl.Schema` and height. A LazyFrame reads one when its unoptimised `explain()` has a `DF [` leaf (`funcs._scans_rows_in_memory`: `input_df.collect().lazy()`, `pl.LazyFrame({...})`, the prediction's empty frames), and its serialised plan would carry those rows to core. The first is held as the **deferred** record `<job_id>_0` with that plan (as a deferred submit is, so an extension dtype reaches the consumers that run it), the second as the materialised record `<job_id>_0` of the file. A SQL Query run's body is `SqlQueryInput` (the node's `sql_code`, its `inputs` as serialised plans (base64) in connection order, `flowfile_flow_id`, `flowfile_node_id`), with `extra="forbid"`; its child is `funcs.sql_query`, pooled, which validates the statement itself (`shared.sql_validation`, as the catalog editor's `execute_sql_query` does), registers the input plans as `input_1..N` in a `pl.SQLContext` and translates the statement once. Both children report what the code answered through `funcs._user_code_result` and both routes hold it through `_hold_user_code_result`, so a query's result is held by the same rule as a Polars Code result's. `job_id` is a required query parameter matching `^[A-Za-z0-9_-]+$`, because it names the output files: the job runs under it, so `GET /v1/jobs/{job_id}` answers it and `POST /v1/jobs/{job_id}/cancel` stops it; its entry stays `Completed` with `results` reset to `None` (the task routes' `/status/{id}` reads it too) and is stamped when the job ends, so the age sweep drops it. The child is the one the kind's task route spawns (`generic_task` over the reader, `fuzzy_join_task`, `custom_node_runner`, `train_model_task`, `apply_model_task`), and for a random split `funcs.split_result`, which collects the rows once and writes each split's slice to its own file, the last split taking what rounding leaves. Output *i* is held as the materialised record `<job_id>_<i>`, never under the job id and never in a task route's `<task_id>.arrow`, at `result_path(flow_id, "<job_id>_<i>")`, a custom node's output at the path its runner reported (`<…>_0__<name>.arrow` for every output but the first); each is stamped when it is put, so `sample`, `count`, `HEAD`, `DELETE` and the age sweep treat it as a submit's, and releasing one output leaves the others held. A split's columns are the plan's `pl.Schema` its child queues (`{columns, row_counts}`); every other output's columns are read here from its file's schema, so an unregistered extension dtype comes back as its storage type, as on the task routes, and its row count is the one the child rode along (a fuzzy join's and an apply's are counted here from the file). A training's one output is the model it fitted, a blob record `<job_id>_0` (no columns, no row count) of the file the child wrote at `result_path(flow_id, "<job_id>_0")` with a `.blob` suffix, which `HEAD`, `DELETE`, the age sweep and the blob export treat as any held blob. An apply looks its model up once the sweep and the release have run: one not held is 404 and a held result that is no blob 422, before anything runs, and the child reads the model at that record's path. Outputs are keyed `result` for the reads, the fuzzy join and an apply, `model` for a training, by declared output name for a custom node and by split name for a random split. `metadata` is `{}` except for a Kafka read that consumed messages, which carries the `KafkaReadResult` its child wrote beside the rows (`<file>.offsets.json`, read and deleted here), and a training, which carries the `{sha256, size_bytes, model_type}` its child queued for the model it wrote. Before the child runs the route sweeps expired results and releases what was held under the job id and its output ids, so a rerun replaces its outputs and is not swept while it runs; a child that does not complete, a cancelled one included, leaves none of the files it was to write and the route answers the submit's 500 `{status, error_message, error_kind}`; a bad body or job id is 422. `split_result` is not an `OperationType` and is poolable.
- **What the worker declares** (`protocol_routes.worker_capabilities()`, the answer of `GET /capabilities` and `GET /v1/capabilities`): `operations` is `OPERATIONS`, the nineteen `OperationKind` values this worker runs, the twelve `/v1/ops` kinds and the seven the task routes serve (writes, Delta, visualisation sessions), a kind listed while a route here runs it; `read_schemes` and `write_schemes` are `CLOUD_SCHEMES` (`s3`, `az`, `gs`) and `https` (a Read node's URL as well as the presigned URLs a blob is copied to and from), plus `file` when `FLOWFILE_WORKER_LOCAL_FILES` is `1`, read on each request so one process answers either way without a restart, and `read_schemes` also `http` (the child that runs a Read node's plan or its `file_read` fetches its `http` or `https` URL; for a `/v1` deferred submit with no preview the child that resolves the plan's columns first fetches what that reads, for a CSV up to `infer_schema_length` rows, and the child that later samples, counts or exports it fetches the URL again; nothing writes to an `http` URL); `credential_resolution` is `master_key`. The desktop shell (`flowfile_frontend/src-tauri/src/env.rs`), the root `docker-compose.yml` and single-file mode (`flowfile/flowfile/web/__init__.py::include_worker_routes`, in core's process for the worker it co-hosts) set the variable for a worker on core's host, which sees core's files; a worker on another host leaves it unset.
- **Catalog reads** go exclusively through `catalog_reader.open_catalog_table` (`scan_delta`) / `open_virtual_result` (`scan_ipc`); both validate paths under `storage.catalog_tables_directory` / `catalog_virtual_results_directory` via `shared.delta_utils.validate_catalog_path`. Don't `scan_delta`/`scan_ipc` catalog paths inline.
- **Delta writes** (`funcs.write_delta`, `merge_delta`, `scd2_delta`) write to the `output_path` they are given or, given a catalog table by identity (`table_name`, a bare directory name, and `table_id`, named in the start log line), to that name joined onto the `storage_payload`'s `base_uri` or onto this worker's `storage.catalog_tables_directory`, unresolved, as `/catalog/materialize` joins a new table (`_delta_target`); a name with a separator or `..` fails the task, and the report's `table_path` is the location written. The `storage_payload` is `models.DeltaStoragePayload` (`connection`, an optional `base_uri`, `extra="forbid"`), validated by `funcs._storage` before it is read, so an unknown key fails the task; the report each queues is `models.DeltaWriteReport` (`Scd2WriteReport` for an SCD2 write, with its `version` and `scd2_metrics`) or `DeltaSkipReport`, dumped by alias (`schema`). `shared/tests/test_worker_contract.py` pins both with the task's parameters (`TASK_RESULTS` names the reports), so a change to either needs a new `PROTOCOL_VERSION`.
- **`resolve_virtual_table` has two sanctioned targets** (`funcs.py`): the default `virtual_results` (worker-private `catalog_virtual_results/`, idempotent cache named by `(table_id, sha256(plan_bytes + source_versions_hash))` — plan bytes rotate the file when the producer's output changes, the versions hash when a fingerprinted Delta source changes; a `NO_VERSIONS_HASH` ("noversions") key **always rebuilds** because it proves nothing) and `kernel_shared` (`storage.shared_virtual_results_directory`, kernel-readable catalog-view snapshots, caller-named) which **always rebuilds** — serialised-plan hashes don't change when referenced Delta data does, so an exists() cache would serve stale data. Both targets prune superseded same-table snapshots older than `_SUPERSEDED_MIN_AGE_S`. The child collects with `engine="streaming"` and writes `compression="lz4"` — `write_ipc` defaults to **uncompressed**, and dictionary-encoded Parquet strings expand many-fold when written out raw (uncompressed, a 294 MB source snapshots to 4.9 GB).
- **Viz sources are lazy handles, not snapshots.** `_build_viz_loader_in_child` returns a LazyFrame for every kind — `physical` is `scan_delta`, `sql` is a `SQLContext` over live scans, and `plan` deserialises a flow node's shipped `pl.LazyFrame` — so Polars pushes each chart's projection into the source. Only `ipc_path` (catalog virtual flow tables) reads a materialised file, and that file is written by `funcs.resolve_virtual_table`, never by the viz child. Deserialisation must stay inside `_build_viz_loader_in_child`: `test_catalog_visualize.py` asserts `polars_gw` never reaches the FastAPI parent.
- **Module-top polars imports** (`funcs.py`, `catalog_reader.py`, `viz_session_worker.py`) are fine because they're invoked in children; do not import them eagerly into the FastAPI request path.
- `secrets.py` re-derives user keys independently of core using the same `$ffsec$1${user_id}${token}` format (`SECRET_FORMAT_PREFIX`) and `KEY_DERIVATION_VERSION = b"flowfile-secrets-v1"` HKDF salt — keep these byte-for-byte in sync with core's secret module or decryption breaks.
- `TEST_MODE` (env `TEST_MODE` set) returns a fixed master key; tests set it in `conftest.py`. Note core's suite spawns the worker **without** `TEST_MODE`, so there the worker reads the real store.
- `secrets.py`'s store dir honors `FLOWFILE_SECURE_STORAGE_PATH` (else `$APPDATA`/`~/.config` + `flowfile`), matching `flowfile_core/auth/secrets.py`. The two resolvers must stay in lockstep: core encrypts `$ffsec$` with the master key in that dir and the worker re-derives it, so a split store turns every secret-touching offloaded job into "Task failed" — for a core-built cloud read, `CredentialDecryptionError: Could not decrypt the cloud storage credentials embedded in this query plan…`.
- **Core-built cloud plans carry their credentials encrypted**, as a Polars `credential_provider` (`shared.cloud_credential_provider.EncryptedCredentialProvider`) rather than in `storage_options`; it decrypts through the decryptor `utils.py` registers, which imports `secrets` only at first use so pydantic stays out of children that never read cloud data. A child that never imports `utils` (the viz child) cannot execute such a plan. With `FLOWFILE_COMPUTE_PROTOCOL` on in core, a read of a saved connection carries a `shared.cloud_credential_provider.CredentialRefProvider` instead, resolved in the worker: by the child that resolves a `/v1` deferred submit's columns, as resolving a scan's columns calls its provider, and by the child that collects, samples or exports the plan. Either looks the connection up in the catalog database the worker is configured for (`FLOWFILE_DATABASE_URL`, else `FLOWFILE_DB_PATH`, else the SQLite file under its storage dir; co-located that is core's file, on another host it must be the deployment's shared Postgres catalog) and decrypts its secrets with the worker's master key, and an `aws-cli` profile or `iam_role` role resolves with the worker's AWS identity, not core's.
- **`external_sources/s3_source/models.py` hand-mirrors core's cloud connection and write models.** `FullCloudStorageConnection` must carry every field `build_storage_options` reads (including `aws_profile` and the encrypted `aws_session_token`), and `WriteSettings.resource_path` re-runs `shared.cloud_storage.utils.validate_cloud_resource_path` (422 on an empty or relative path) as a second line of defence behind core, which owns the docker-mode local-path refusal.

## Running / entry points
- Poetry script: `poetry run flowfile_worker` → `flowfile_worker.cli:run` (a thin shim; `main.py`'s imports stay out of the launcher module).
- Module: `python -m flowfile_worker` → `__main__.py` (Docker `CMD`).
- **Never point either entry point back at `main.py` directly.** A launcher whose `__main__` has no `__spec__` (console script) or a non-`.__main__` spec (`-m flowfile_worker.main`) makes spawn re-execute it in *every* child, re-importing the whole FastAPI app: 1249 modules per child vs 345 today. The first child started through `mp_context` stamps a `flowfile_worker.__main__` spec in the parent (`SpawnProcess.start` in `__init__.py`) to force spawn's free path; `tests/test_import_purity.py::test_spawned_child_does_not_reexecute_launcher` locks it in, along with the child's module ceiling and the set of modules the tasks must import at use.
- Flags: `--host`, `--port` (default 63579), `--core-host`, `--core-port` (default 63578); also `CORE_HOST`/`CORE_PORT` env (Docker). `FLOWFILE_WORKER_TLS_CERT` and `FLOWFILE_WORKER_TLS_KEY` (paths to a PEM certificate and its key) make `main.run()` hand them to uvicorn as `ssl_certfile`/`ssl_keyfile`, so the worker serves `https`/`wss`; unset, it serves plain HTTP.
- Docker: `flowfile_worker/Dockerfile` (python:3.12-slim, `FLOWFILE_MODE=docker`, EXPOSE 63579, healthcheck on `/docs`).

## Gotchas
- `POST /shutdown` answers only a loopback transport peer (403 otherwise; forwarded headers are not consulted). The desktop shell posts from the same host and Docker stops the container with a signal, so nothing remote needs it; do not relax it, use a token-gated route instead.
- `GET /capabilities` is core's handshake: it reports what `shared/compute_protocol.py::local_capabilities()` builds with the worker's declarations. Core refuses to send any work when the app, protocol or Polars version or `polars_runtime` differs from its own process; otherwise it narrows what it places here: a plugin version that differs, or a probe plan that fails here (one per expression plugin and one carrying a Python function, each run as an ordinary submit under result id `handshake-<probe>-<hex>`, sampled and released), refuses only the nodes that need it. `python_version` is compared and listed, `platform` and `plugin_libs` are reported and not compared; `operations`, `read_schemes`, `write_schemes` and `credential_resolution` are declarations and are not compared. Which plugins are reported and how their library paths resolve is defined in `shared/compute_protocol.py`, not here. A request on any `routes.py` route carrying a foreign `X-Protocol-Version` is answered as usual and logged as a warning.
- Adding a new `OperationType`: it must be both a literal in `models.OperationType` AND a function name on `funcs` — both `spawner.start_process` and `streaming._spawn_subprocess` do `getattr(funcs, operation)`. If it follows the uniform kwargs contract and is safe to run in a reused child, also add it to `pool.POOLABLE_OPERATIONS`; otherwise it silently always takes the spawn-per-task path (the safe default).
- **Warm pool reuse rules** (`pool.py`): a member is reusable only when its completion envelope was drained — cancel (`/cancel_task` terminates the member), task timeout, a crash, or a missing envelope all retire it, and the next `acquire` spawns a replacement (a cancel storm degrades to spawn-per-task, never worse). Never pool `execute_custom_node` (arbitrary user Python with imports) or `fuzzy` (positional-arg spawn); `polars_code` is pooled, as its sandbox allows no import and no dunder access, and so is `sql_query`, which runs no Python of the user's, only Polars' SQL translation over plans. Parent-side `PoolMember.submit` fully zeroes the error `Array` and resets progress *before* the put — funcs targets write errors without a terminator, so skipping the zero-fill leaks the previous task's error tail into shorter messages.
- `status_dict`, `PROCESS_MEMORY_USAGE`, and the `ProcessManager` map are plain in-memory dicts in the parent — task state does not survive a worker restart; `clear_task` is the only thing that removes a legacy task's IPC file + state (and the Kafka `.offsets.json` sidecar), `DELETE /v1/results/{id}` and the age sweep each submit runs (`protocol_routes.sweep_expired`) the only things that remove a `/v1` result's. Core sends the `DELETE` for every result a node minted, together: on a rerun under another hash, on the node's removal, when its flow closes, when a published-API call has answered and when a headless run ends. The sweep, `CACHE_EXPIRATION_TIME` (24 h, a constant in `__init__.py`) after the submit ended, is the backstop for a core that died without closing its flows, never the way a result is meant to go.
- On WebSocket client disconnect mid-task the subprocess is **handed off** to a daemon `handle_task` thread (`_handoff_to_background`), not killed; `p`/`progress`/`error_message` are nulled so the `finally` block doesn't reap them.
- Connectors do blocking network I/O; they MUST run in the subprocess (via `start_generic_process`), never inline in the async endpoint, or they block the event loop.
- Viz sessions are long-lived spawned children with idle-TTL reaping (`VizSessionRegistry.IDLE_TTL_SECONDS = 300`, background reaper thread); shut them down via the lifespan, evict via `/catalog/visualize_evict`.
