# CLAUDE.md - flowfile_frame

A Polars-like programmatic Python API that builds Flowfile ETL graphs under the hood. Package-specific notes; see the root `/CLAUDE.md` for monorepo-wide setup, build, lint, ports, and cross-package contracts.

## Role
`flowfile_frame` (imported as `import flowfile_frame as ff`) is a Python library giving a Polars-`LazyFrame`-like surface (`FlowFrame`, `Expr`/`Column`). Every method call appends a node to an **in-process `FlowGraph`** instead of (only) computing data.

It is **NOT independent of the backend**: it imports `flowfile_core` directly (`flowfile_core.flowfile.flow_graph.FlowGraph`, `flowfile_core.schemas.*`, `flowfile_core.database.connection`) to construct/mutate the same DAG the Designer UI and core executor use. It runs in-process — no HTTP, no ports. The graph it builds can be saved (`.flowfile` via `save_graph`) and opened in the Designer, or executed via `.collect()`.

Runtime contract: each `FlowFrame`/`Expr` carries a `_repr_str` — a literal Polars source-code string. Complex operations are serialized into graph nodes via the `_add_polars_code` path in `flow_frame.py` (which calls `flow_graph.add_polars_code`); simple ones map to dedicated node settings (`add_sort`, `add_manual_input`, etc.). The generated string must be valid, executable Polars code, since core re-evaluates it.

The kernel holds no catalog database, so a cell that opens one itself stops with `NO_DATABASE`, which names where it was opened (`_opened_from`: `a cell`, else the frame module of a regression) and the `ff` functions to use; the listener runs before pysqlite would create the file. A script and the tests' kernel-sim never set the variable.

So a script cell run again unchanged keeps its canvas rows, an edited one is run by core, and only core's refusals (writers, types outside its allowlist) still say "Push". `NotebookMode.schema_resolver` is `_Session.held_schemas`: a deferred node a cell builds whose seed has no columns (`native.resolved_seed`, at the three non-sync seeding sites) takes its twin's columns, else what core predicts from its settings and its inputs' columns (`schema_only`); a sync never asks. `_Session.refresh` runs before and after every `execute` and before `schemas`: it keeps the schemas core sends for canvas nodes that ran on the snapshot, then seeds every deferred node standing for a canvas node (`_twin`) with that node's schemas when they differ, reads the nodes computed below it again and re-points the deferred frames bound in the namespace (`FlowFrame.data` is a plain attribute, so a re-seeded node alone would leave them on the old placeholder). A read of a file a cell names keeps its canvas rows and is never re-seeded; `refresh` runs under `paths_as_written()` itself, since `_kernel_hidden_path` answers `None` without it and a `schemas` call does not set it (frames built on that read are not deferred and would compute on the placeholder). The calls go through `_refreshed`, which never fails the op. A rows file core has since removed is asked again (`_fetch`). A push's clean run computes nothing: `_clean_run` gives core's runner `_clean_run_rows(flow_id)` as its `canvas_rows` (`clean_run(canvas_rows=)` above).

## Key patterns & conventions
- **Source string is load-bearing.** When adding/altering an `Expr` or `FlowFrame` method, ensure `_repr_str` builds correct Polars code (use `pl.` prefixes for dtypes/classes, mirror Polars signatures). A wrong string breaks graph execution silently.
- **Two emission paths.** Prefer a dedicated core node setting when one exists; fall back to `_add_polars_code` only for genuinely complex expressions (`use_polars_code_path` flags in `flow_frame.py`).
- **`drop`, `filter` and `when` lower natively.** `drop(names)` → `NodeSelect` with the dropped columns `keep=False` and `keep_missing=True` (selectors, or a missing name under `strict=True`, stay on the Polars-code path). `filter(*predicates, **constraints)` → `NodeFilter(advanced)` when every predicate has an `_ff_repr` (comparisons, `&`/`|`/`~`, `is_in`, `is_null`, the mapped `.str`/`.dt` helpers), joined with `and`; `filter_split` reuses the same predicate text and raises `ValueError` when there is none (no Polars-code fallback for a two-output node). `When` keeps an `if … then … elseif … else … endif` `_ff_repr` (no `otherwise` ⇒ `else null`), so `with_columns([when(...)...alias(x)])` becomes a Formula node. Every lowering first runs `_formula_parses` (core's parser accepts the text) because a Filter node silently keeps nothing on a parse error; string literals take whichever quote kind the value lacks — the parser has no escape, so a value with both kinds has no formula form. Polars-code nodes emitted without a `description` get a derived label (`Add columns: x`, `Filter on: a`, `Sort by: a`) instead of the UI's truncated first code line. Tests: `tests/test_native_nodes.py`.
- **`with_columns` emits at most one Formula node.** Expressions that all have an `_ff_repr` become ONE `NodeFormula` with one entry per expression, in argument order — but only when they are *independent* (`flowfile_core.flowfile.formula_dependencies.entries_are_independent`: no expression reads a column another writes; reading the column it writes itself is fine, an unparseable formula fails closed). Formula-node entries evaluate SEQUENTIALLY while Polars' `with_columns` evaluates in parallel, so dependent expressions (`(col("x")+1).alias("x")` beside `(col("x")*2).alias("y")`) skip the formula path entirely and emit a Polars-code node, preserving Polars semantics. The `flowfile_formulas=` kwarg is the sequential contract by design and always emits one multi-entry node (`_with_flowfile_formulas`), no independence check. **The two directions are deliberately asymmetric**: import collapses independent expressions into one N-entry node, while export always chains one `with_columns` call per entry (`code_generator`), so a multi-entry node re-imports as N single-entry nodes rather than round-tripping as one. Tests: `tests/test_with_columns_multi_entry.py`.
- **Partition aggregates lower onto the Window node.** `Expr.over()` records a structured `_window_spec` (`{column, function, partition_by}`) when the base is exactly `pl.col(x).<agg>()` with `agg` in `transform_schema.AGGREGATE_WINDOW_FUNCTIONS`, the partition is plain unaltered columns, and no `order_by`/`descending`/`nulls_last`/non-default `mapping_strategy` was given; `alias()` carries it, any other method drops it. `FlowFrame.with_columns` → `_try_native_window_functions` emits one `NodeWindowFunctions` when every expression has a spec, all share the same `partition_by`, and every output name differs from its source column (the node's schema callback appends columns, so an unaliased overwrite stays on the polars-code path). Tests: `tests/test_window_lowering.py`.
- **Methods are injected**, not all hand-written: `FlowFrame` is decorated with `@add_lazyframe_methods`; `Expr` via `add_expr_methods(Expr)` at module end. Passthrough methods (`PASSTHROUGH_METHODS`) just delegate to the cached Polars object; explicitly-defined methods (e.g. `collect`) are never overwritten by the decorator.
- **Native node classes and deferred frames.** Node types with no fluent method are placed by classes on the `NativeNode` base (`native.py`); user docs: `docs/users/python-api/reference/native-nodes.md`. Invariants:
  - `_build` follows canvas order: `merge_frames` (only when flow ids differ; remaps the passed frames in place and leaves other graph handles stale) → `allocate_node_id` (never behind the process counter or the graph's max id; `add_node_step` silently replaces a same-id node) → settings with the base-managed fields (`flow_id`, `node_id`, `pos_x/pos_y=0.0`, `is_setup`, `user_id`, `depending_on_id(s)`) → promise → wire → `graph.add_<type>` (keyed-input nodes such as `run_flow`: add first, then wire) → add-time diagnostics → one frame per output handle, named from the settings' `output_names`. A failed build deletes the node again. Subclasses customise it through hooks, not by overriding `_place`/`_build_outputs`: `_add` (the add call; `CustomNode` uses `add_user_defined_node`), `_seed_schemas` (per-handle seed schemas; `RunFlow`, `CustomNode`) and `_build(handles=...)` (explicit target handles; `RunFlow`'s keyed slots).
  - **Building never runs a deferred node.** `DEFERRED_NODE_TYPES` (run_flow, python_script, GA/external sources), kernel, prediction-blocked and `node_type == "output"` custom nodes (`CustomNode` defers these itself), installed local custom nodes on a non-local graph (the worker would run them; a class with no node file runs in core and builds eagerly), and side-effect nodes (`is_side_effect_node_type`: `output`-group templates, custom templates with `node_type == "output"`, plus the model nodes) below a deferred frame or a gate are **seeded** with typed zero-row outputs (`seed_deferred_node`: `resulting_data`, `_named_outputs`, `_named_schemas`, `deferred_until_run=True`) instead of executed; `seeded_at_build` is the one predicate `_create_child_frame` and `NativeNode` share (the gate walk runs only for side-effect types), so a writer below a gate writes when the run reaches its live side. `FlowFrame._deferred` propagates through `_create_child_frame` and every multi-input op (`any(...)` of the inputs); `combine_flow_graphs_with_mapping` carries seeds, and every built or run result, across a merge (a node that already ran has lost its flag, and must not re-execute on the merged graph). `seed_deferred_node` also sets `FlowNode.placed_deferred` (carried by `merge_frames`), so `FlowNode.reset()` re-arms `deferred_until_run` and `materialise` re-seeds the dropped placeholder (`_reseed_lost_placeholders`) instead of running the node. `deferred=False` over a deferred input raises (`NativeNode._decide_deferred`).
  - `collect()` and the materialising passthroughs (`MATERIALISING_PASSTHROUGH_METHODS` in `lazy_methods.py`) on a deferred frame call `_materialised_lazyframe`: `run_graph(node_ids=...)` on the node's lineage (`ancestors`) only, so writers and sources on other branches do not run, success judged on that lineage, a dead gate exit read from `flow_graph.last_closed_gate_handles`. Frames below a gate (`_below_a_gate`: the node or an ancestor is a gate) take the same run-then-read path; only frames with no gate and no deferred ancestor collect their build-time plan.
  - A seed lost to an in-place reset and read outside `materialise` surfaces as core's `DeferredNodeError`, translated by `lost_placeholder_error`; build-time-effect paths on deferred frames (`sink_*`, `inspect`, Polars-code writer and serialize fallbacks) raise instead of baking the placeholder into a node, and `sink_*`, `inspect` and the writer fallbacks raise below a gate too (`_below_a_gate`).
  - **Transform and native-node build-time reads go through `native.materialise`**, so `${name}` resolves like the run loop (`node_parameters_resolved`) — for the node and every result-less ancestor the read re-executes (after a merge or `FlowGraph.reset()`) — and an undeclared reference raises `NativeNodeError`, even on a graph without parameters. It re-seeds lost placeholders first and translates any remaining `DeferredNodeError`. Source readers and connectors (`flow_frame_methods.py`, `catalog.py`, `database/`, `kafka.py`, `rest_api.py`) read `get_resulting_data()` directly, so `${name}` in their settings is not resolved at build.
  - Every user-facing error is `NativeNodeError`; translate FastAPI `HTTPException` (e.g. via `add_connection_checked`) and `flowfile_core.catalog` errors (chained with `from`), never let them escape.
  - **Fluent native nodes write no default description** (the canvas generates its own; a rebuilt node must not carry text the canvas never had); polars-code fallbacks keep their derived labels. `FlowFrame.polars_code(code | fn, *others)` places exactly one `polars_code` node (a function's def line is dropped, a lone `return <expr>` stores `<expr>`, a trailing `return output_df` is dropped); `with_row_index(name, offset, group_by=)` is always one `record_id` node; list `on=` takes `unpivot`'s native path; `std()`/`var()` with `ddof=1` are native aggregations; `PythonScript(schemas=)` and `@python_script(returns=)` persist `NodePythonScript.output_schemas`. Tests: `tests/test_fluent_native_nodes.py`.
  - **Custom nodes stay eager at build** outside the deferral cases above; `deferred=` overrides, secrets never auto-defer, and a `ff.Parameter` setting is stored as `${name}` (must be declared on the graph).
  - **`ff.custom_nodes.install(Cls)`** writes the class, its same-module `NodeSettings` classes and the imports they use to `<key>.py` (`_class_file_source`: each class comes with its own `_Fragment` — file, notebook cell or console selection, via `_defining_module` → `_console_source.console_class_source` — so settings classes run as separate console selections are carried too, and written in dependency order (`_dependency_order`); a name no kept import covers is re-imported with the console statement that bound it (`_console_source.console_import_for`), else from where the class's globals say it lives (`_import_for`: modules, and classes/functions of another loaded module), and any other module-level name is refused), then loads it as the designer does (`registry.load_file` + `registry.ensure_class`) and restores the previous file and template when it does not load; `custom_node._INSTALLED_CLASSES` lets `_register_class` accept that class for the installed key. An unknown `ff.custom_nodes.<name>` raises `CustomNodeLookupError`, a `NativeNodeError` that is also an `AttributeError`.
  - **`@python_script` cell layout is a contract.** `python_script._notebook_cells` emits, in order and each only when non-empty: the prelude (imports of modules the body reads from its module, then constants) / the inputs cell (`INPUTS_MARKER` `# flowfile: inputs`, then `<param> = flowfile_ctx.read_inputs()["main"][i]` per parameter) / the docstring as a `#` note / the body split at `# %%` and `# %% [markdown]`, dedented / the last cell, where the top-level `return` becomes `OUTPUTS_MARKER` `# flowfile: outputs`, `_result = <expr>` and the publish (`flowfile_ctx.publish_output(_result, "<output>")`, behind an `isinstance(_result, dict)` guard when there is no `outputs=` and the value is not a call, or the key-checked loop for a dict). A function without a `return` of its own is a script (`_is_raw`): no parameters, so no inputs cell, nothing rewritten, so no outputs marker, and its body must name `flowfile_ctx.publish_output` (`_check_raw`); it takes any number of frames in the call. The notebook render (`flowfile_core` `native_handlers._decorated_script`, a Python Script node back into a function) pattern-matches this layout and the two marker comments (refused inside the body), and writes cells holding neither marker as such a script, so change them only together with it. Tests: `tests/test_native_python_script.py`; `docs/examples/native_nodes.py` pins the documented example's cells verbatim.
  - **Text entry points (no function object).** The notebook interpreter in core holds only cell text, so the two `def`-taking nodes also build from source: `flow_frame._polars_code_text(source)` (a `_PolarsCodeText` passed as `code` is stored as it is) and `PythonScriptFunction._from_source(code, first_line, namespace, ...)` → `python_script._source_cells`, which checks the decorated block with `symtable` and an AST screen instead of `compile`. Checks, messages and stored settings equal the function path's, a script without a `return` included, so node hashes match; `.fn` is `None`. Tests: `tests/test_notebook_text_entries.py`.
  - **Import-cycle rule:** `native.py` must not import `flowfile_frame.flow_frame` at module level (`flow_frame` imports from it); import `FlowFrame` inside functions or under `TYPE_CHECKING`, as `_build_outputs` does.
- **Polars re-exports.** `__init__.py` re-exports Polars dtypes and aliases `LazyFrame = DataFrame = FlowFrame` for generated-code compatibility — keep these when touching exports.
- Follow root-doc rules: Polars only (never pandas); imports ordered stdlib → third-party → first-party.

## Running / entry points
Library only — no server/CLI of its own. Usage: `import flowfile_frame as ff`, build a graph, then `frame.collect()` (returns `pl.DataFrame`), `frame.save_graph("p.flowfile")`, or `open_graph_in_editor(frame.flow_graph)` (from `flowfile.api` in the `flowfile` package). Backend modules load in the same process; no port is bound.

## Gotchas
- **Stub gate.** Public surface of `FlowFrame`/`Expr`/submodules ships committed `.pyi` stubs (+ `py.typed`). After any public API change run `make stubs` (root) and commit; `make check_stubs` is the CI gate that fails on drift. All three generators run from `make stubs`: `expr_stub_generator.py` → `expr.pyi`, `flow_frame_stub_generator.py` → `flow_frame.pyi`, and `submodule_stub_generator.py` → every other `.pyi` **including `__init__.pyi`** (it walks all `.py`, excluding `expr.py`/`flow_frame.py` and private `_*.py` modules). `make stubs` then runs `ruff --select F401 --fix` to prune unused imports.
- **Stubs of the native node modules.** `enums`, `native`, `gate`, `parameters`, `run_flow`, `custom_node`, `custom_nodes`, `kernels`, `python_script` and `sql_query` get their `.pyi` from `submodule_stub_generator.py`, which copies annotations verbatim (the `Literal`s reach the stubs), keeps `@property` but drops other decorators, renders enum members, and drops every dunder outside `_PUBLIC_DUNDERS` (`__init__`, `__call__`, `__getitem__`, `__getattr__`, `__contains__`, `__dir__`, `__iter__`, `__len__`): public classes need an explicit `__init__`, and a module-level object reaches the stub only when annotated (`custom_nodes: CustomNodes = CustomNodes()`). `__init__.pyi` leaves out the `from . import <sub>` re-export of a submodule shadowed by a same-named export (`custom_node` and `python_script` are the functions, `custom_nodes` and `kernels` the singletons). A new `.pyi` must be `git add`ed — `make check_stubs` only diffs tracked files.
- **Console source comes from an audit hook.** `_console_source.py` (imported by `__init__.py`) adds a `sys.addaudithook` hook only in an interactive interpreter (`sys.flags.interactive`, `sys.ps1`), PyCharm's console (`pydevconsole` loaded) or with `FLOWFILE_CONSOLE_SOURCE` truthy, because an audit hook cannot be removed; `install_hook()` opts any other console in. The hook records each source compiled under `<input>` / `<console>` (PyCharm's console and the `code` module never fill `linecache`); `callable_utils._read_source` falls back to `console_function_source` when `inspect.getsource` raises `OSError`, for `@python_script` functions and `map_elements` lambdas alike; `custom_nodes._defining_module` falls back to `console_class_source`, which returns the whole selection (a class with own methods is verified by their code objects, since pydantic adds `model_post_init` from its own file, and every class by the literals its body assigns, compared with pydantic field defaults or class attributes; a method-less `NodeSettings` class otherwise takes the newest fragment defining its name — the hook therefore also keeps fragments containing `class ` and `import `, the latter for `console_import_for`). A fragment answers only when recompiling it yields a code object equal to the function's and its literal defaults match: name + line alone would hand a stored lambda the text of a newer one on the same line. The allow-list stays short because `<stdin>` raises the event without the text and `<string>` holds generated code (dataclasses, namedtuple, pydantic), not the user's; fragments never go into `linecache`, where `inspect` matches by line alone. The hook sees only code compiled after it installs, so `install_hook` records the selection running at that moment (the one that imports flowfile itself, PyCharm's usual "execute selection" of a whole script) from the stdlib `code.InteractiveInterpreter.runsource` frame on the stack, which PyCharm's `pydevconsole` and `code.interact` both call; lookups read running selections from the same frames.
- Don't break the `LazyFrame`/`DataFrame` aliases or Polars dtype re-exports in `__init__.py` — generated flow code depends on them.
- Per the user memory rule, core must not `.collect()` LazyFrames internally; `FlowFrame.collect()` here is the intended user-facing materialization point.
- DB/cloud/catalog helpers persist via `flowfile_core` (`get_db_context`, core's connection manager) — they touch core's storage, not a local file.
- **Cloud Delta mirrors the catalog's merge/change-feed kwargs, minus cursors.** `FlowFrame.write_delta` / `write_to_cloud_storage` take `merge_keys` and `track_changes` (Delta-only guards like `partition_by`'s), and `scan_delta` / `read_from_cloud_storage` take `changes_since` + `include_change_preimage` through `catalog._resolve_change_mode`; `changes_since="last_run"` raises for cloud paths (no cursor store) and `version`/`delta_version` plus `changes_since` is a `ValueError`. Cloud writes run when the method is called, not at `.collect()`.
